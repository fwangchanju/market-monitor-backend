# 백로그

앞으로 할 일과 그 일의 배경·구상·선행 조건을 함께 적어둔다.

## 이 문서의 규칙

- 설계·문서 담당 세션만 수정한다. 구현 세션은 읽기만 한다
- 목록만 적지 않는다. "어떻게 하려고 했더라"를 다시 떠올리지 않아도 되게 배경과 구상까지 적는다.
  같은 설명을 반복하지 않는 것이 이 문서의 목적이다
- 우선순위나 일정은 정하지 않는다. 착수할 때 정한다
- 완료되면 이 문서에서 지우고, 남길 판단이 있으면 `docs/decisions.md`로 옮긴다

> 이미 결론이 난 사안(왜 A 대신 B를 골랐나)은 `docs/decisions.md`에 있다. 이 문서는 아직 안 한 일만
> 다룬다.

## 구획 — 지금 무엇을 확정하고 무엇을 열어두는가

시간외 등락률, 회원가입, 집계 테이블 제거가 한 덩어리로 얽혀 있어서 한 번에 결정하기 어렵다.
**의존 관계로 잘라 구획을 나눈다. 지금 확정하는 것은 구획 1뿐이고, 구획 2의 내용은 아래 각
항목에 적혀 있되 "미확정"이다.** 구획 1이 끝나기 전에는 구획 2를 다시 논의하지 않는다.

| 구획 | 내용 | 무엇에 걸려 있나 |
|---|---|---|
| **0** | 렌더러 장애 / 스냅샷 실삭제 전환 | 아무것도 — 서로도 독립, 아무 때나 |
| **1** | 시간외 등락률 + 마켓 지수 바 + 공휴일 판정 | 없음 ← **지금 하는 것** |
| **2** | `userId` + 멀티테넌시 + 과거 날짜 조회 | 구획 0의 실삭제 전환 |

### 집계 테이블 제거는 결정 사항이 아니다 — 측정 구획을 없앴다

한때 "집계 테이블을 없앨지 측정해서 정하는" 구획을 맨 앞에 뒀다. **없앴다. 잘못된 구획이었다.**

- **제거는 멀티테넌시가 강제한다.** `category_id`가 사용자별이 되는 순간 집계 행도 쓰기 부하도
  사용자 수만큼 곱해진다. 측정 결과가 어떻게 나오든 이 테이블을 사용자별로 유지하는 선택지는
  없다. 측정이 답할 수 있는 질문이 아니었다
- **"되돌릴 수 없다"를 과하게 잡았다.** 등락률이 바뀌는 구간은 15:40~20:00인데, 정리 배치
  (`SnapshotRetentionScheduler`, 두 테이블 모두 10일)가 **장마감 시각이 아닌 행을 전부 지운다.**
  즉 잘못된 값이 들어가도 10일 뒤 사라진다. 영구 보존되는 것은 종가 시각(15:30, 15:35)인데
  그 구간은 키움 값 그대로라 애초에 안 바뀐다

측정이 필요해지는 시점은 따로 있다 — 구획 2에서 집계를 **실제로 없앨 때**, 캐시 없이 견디는지.

**그 측정을 구획 1이 대신 해준다.** 시간외 등락률은 집계 테이블을 건드리지 않고 조회 시점에
계산하기로 했다(아래 「결정 1」). 시간외 토글을 켠 화면이 곧 "집계 없이 조립하는 화면"이라,
구획 2의 가정을 트래픽 적은 15:40~20:00 구간에서 먼저 재보게 된다. 느려도 그 토글만 굼뜨고
기존 화면은 그대로다.

한때 여기에 "구획 1은 수집 시점 계산으로 바로 간다. 집계 테이블이 살아 있으므로 다른 선택지가
없다"고 적어뒀다. **틀렸다.** 새 기능만 새 방식으로 만들고 기존 것은 구획 2에서 합류시키는
선택지가 있었다.

### 구획 1에 공휴일 판정을 넣는 이유

기술적 선행 조건은 아니다(기준가가 당일 15:35라 "직전 거래일"을 몰라도 된다). **사용자 결정**으로
같이 진행한다. 둘 다 수집기 주변을 건드리는 작업이라 한 번에 보는 편이 낫다.

### 구획 2에 과거 날짜 조회를 넣는 이유

**같은 조회 경로를 두 번 고치지 않기 위해서다.** 멀티테넌시는 `getCustomMarketMap`/
`getCategoryChangeRates`에 "누구의 트리인가"를 넣고, 과거 날짜 조회는 같은 자리에 "언제인가"를
넣는다. 시그니처와 캐시 키가 같이 바뀌므로 따로 하면 두 번 고친다.

### 구획 1과 2의 순서

**1이 먼저다.** 시간외 등락률이 건드리는 `sector_price_snapshot`과 수집기는 **사용자 독립
영역**이라 멀티테넌시와 겹치는 코드가 거의 없다. 반대로 2를 먼저 하면 시간외 등락률을
멀티테넌시 위에서 써야 해서 일이 늘어난다.

## 로그인 기능 도입 (IP 화이트리스트 제거)

**배경**: 원래 개인용으로 만들었고, 일반 사용자 접근을 막을 특별한 이유가 있어서 nginx에서 IP로
차단하는 구조를 썼다. 그 이유가 무의미해져서 IP 차단 자체를 없애기로 했다.

할 일
- Spring Security + JWT 로그인. 구글 계정 연동 방식을 쓰고 싶음
- 사용자별 커스텀 데이터 관리: 기존 커스텀 테이블에 `userId` 컬럼 추가 (사용자마다 화면이 다르므로)
- 기존 데이터는 admin 사용자 id로 마이그레이션
- `domain/access`(IP 화이트리스트, 관리자 토큰)는 이 작업으로 대체되어 사라진다
- 신규 가입 시 초기 적재: 가입이 발생하면 `stock_info` 기준으로
  `market_map_category` / `market_map_stock_category`에 전체 정보를 초기 적재한다

**선행 조건**: 코드 정비(CI·테스트·버그 수정·문서) 완료. 안전망도 문서도 없는 상태에서 인증과 데이터
마이그레이션 같은 위험한 작업을 하지 않는다.

**주의**: `domain/access`가 곧 사라지므로 정비 단계에서 그쪽 코드를 다듬는 것은 낭비다. 실제로
"예외 계층에 403이 없어서 `ResponseStatusException`으로 우회하는 문제"는 정비 범위에서 제외했다.
이 작업에서 새 구조로 제대로 잡는다.

### `/api/admin/` 을 `/api/custom/` 으로 바꾼다

지금 이 접두사가 붙어 있는 이유는 **nginx가 경로로 권한을 판정하기 때문**이다.

```nginx
location /api/admin/ { auth_request /internal/access-check-admin; ... }
location /api/       { auth_request /internal/access-check-general; ... }
```

로그인이 들어오면 권한은 사용자에서 나오므로 **경로가 권한을 의미할 이유가 없어진다.** 그리고 지금
그 밑에 있는 것을 보면 이름 자체가 틀렸다.

```
/api/admin/allowed-ips                  ← 화이트리스트와 함께 사라진다
/api/admin/market-map/categories        ┐
/api/admin/market-map/scale             │ 전부 마켓맵 커스터마이징 —
/api/admin/market-map/stock-categories  │ "관리자 기능"이 아니라 "내 설정"이다
/api/admin/market-map/versions          ┘
```

살아남는 넷은 사용자별 데이터가 되므로(`userId` 컬럼 추가 대상과 정확히 같은 테이블들) `custom`이
맞는 이름이다. 프론트의 `marketMapAdmin.ts`·`MarketMapAdminPage`·`useMarketMapAdmin` 같은 이름도
같이 따라간다.

### 화이트리스트가 없어질 때 같이 봐야 하는 것 — 부하와 남용

**전제를 먼저 바로잡는다. nginx는 지금도 요청을 쳐내주지 않는다.** `auth_request`가 매 요청마다
Spring을 호출하는 구조라, 낯선 IP의 요청도 이미 앱까지 들어온다. 정적 파일(`location /`)까지 그렇다.

```
낯선 IP가 GET /
  → nginx가 Spring의 /internal/access-check/general 호출   ← 여기서 이미 앱이 일한다
  → false → nginx가 403
```

그래서 "화이트리스트를 없애면 서버가 부하를 받기 시작한다"가 아니라, **이미 받고 있고 요청당 비용만
바뀐다.** 지금은 캐시 조회 하나인데, 그 뒤로는 `/api/market-map/custom`처럼 4,300행을 읽는 조회가
된다.

그리고 게이트가 사라지는 것도 아니다 — IP 조회가 토큰 검증으로 바뀔 뿐이고 비용은 비슷하다.
**진짜 새로 열리는 표면은 가입·로그인 엔드포인트**다. 인증 없이 열려야 하므로 무차별 대입과 계정
남용의 표적이 된다. 화이트리스트 시절엔 없던 면이다.

#### 할 일

- **응답 캐싱.** 마켓맵 데이터는 5분에 한 번만 바뀌는데 지금은 요청마다 4,300행을 새로 읽는다.
  TTL 캐시 하나면 그 조회가 5분에 한 번이 된다. 남용 대비이면서 평상시 응답 속도 개선이고, 위
  「멀티테넌시 — 카테고리 집계 테이블을 없앤다」의 "집계 없이 견디나"에도 그대로 먹히는 카드다.
  단 `userId`가 붙으면 캐시 키도 사용자별이 되므로 메모리 상한을 같이 정해야 한다
- **가입·로그인 엔드포인트만 따로 빡빡한 제한.** 일반 API보다 훨씬 낮은 임계로 IP당 분당 N회
- **`ALLOWED_IP` 캐시의 교훈을 반복하지 않는다.** 지금 그 캐시는 `expireAfterWrite(10s)`만 있고
  `maximumSize`가 없다. IP를 바꿔가며 들어오면 10초 치가 그대로 힙에 쌓인다. 사용자 키 캐시를
  만들 때 상한을 빠뜨리지 않는다
- **정적 경로에서 `auth_request`를 떼어낸다.** 지금은 백엔드가 죽으면 nginx가 정적 페이지조차 못
  준다(`auth_request` 백엔드 실패는 500이다). SPA 껍데기는 인증 대상이 아니고 데이터는 `/api/`가
  지키므로, 이 커플링을 끊을 자리가 여기다

### 사용자별 설정 관리

지금 화면 설정이 **두 갈래로 나뉘어 있다.** 새로 만드는 것이 아니라 이미 있는 것을 정리하는 일이다.

```
서버 DB에 전용 테이블로 있는 것           프론트 세션스토리지에만 있는 것
──────────────────────────────           ────────────────────────────
MarketMapScaleThreshold   색상 임계값      marketMap.isCustom           커스텀 모드
MarketValueTierThreshold  시총 구간 정의   marketMap.decimalPlacesIndex  자릿수
MarketMapCategory.is_excluded 섹터 제외    marketMap.stockLabelModeIndex 라벨 모드
MarketMapStockCategory    종목 배정        avgChangeRateUseSimple       평균 방식
                                           tierRangeMin/MaxIndex 등 (총 14개)
```

#### 경계 — 무엇이 존재하는가 vs 어떻게 볼 것인가

| | 어디에 | 페이지 개념 |
|---|---|---|
| **(A)** 카테고리 트리·제외, 색상 임계값, 시총 구간 *정의*, 종목 배정 | 지금처럼 전용 테이블 + `userId` | **없다.** 사용자당 하나 |
| **(B)** 자릿수, 라벨 모드, 뎁스 범위, 평균 방식, 구간 *범위 선택* | `user_preference.payload` (jsonb) | **페이지마다 독립** |

제외 섹터가 이 경계를 잘 보여준다. **"반도체를 제외 목록에 넣었다"는 (A)**이고, **"지금 이 화면에서
제외를 적용할까"(`sectorFilterEnabled`)는 (B)**다. 목록은 하나인데 적용 여부는 페이지마다 다를 수
있다. 시총 구간도 같다 — 경계값 정의는 (A), 어느 구간까지 볼지는 (B).

#### (B)의 저장 방식 — 중첩 record + jsonb 단일 행

```sql
CREATE TABLE user_preference (
    user_id     BIGINT PRIMARY KEY REFERENCES app_user(id),
    payload     JSONB       NOT NULL DEFAULT '{}',
    updated_at  TIMESTAMP   NOT NULL
);
```

**사용자당 한 행이다.** 설정 14개를 다 넣어도 300~500바이트라, 어제 없애기로 한 집계 테이블처럼
사용자 수만큼 곱해지는 문제가 없다(그쪽은 사용자당 2,700행 × 매 tick이었다).

payload는 페이지별로 묶인 중첩 구조다. 자바 쪽은 record 트리로 받고
`@JdbcTypeCode(SqlTypes.JSON)`으로 매핑한다 — `MarketMapCategoryVersion.snapshotJson`이 이미 쓰는
패턴이라 새 기술이 아니다.

```json
{
  "marketMap":          { "decimalPlaces": 1, "stockLabelMode": 3 },
  "categoryChangeRate": { "beforeMinutes": 15, "tierRangeMinIndex": 1 }
}
```

**저장은 payload 전체를 덮어쓴다.** 프론트가 어차피 전부 메모리에 들고 있고 크기가 작다. 탭 두 개에서
동시에 바꾸면 나중 저장이 이기는데, UI 취향이라 감당할 만하다. 거슬리면 그때
`payload || jsonb_build_object('marketMap', …)`로 가지만 갈아끼우면 되고 **스키마는 안 바뀐다** —
중첩 구조를 지금 잡아두는 값어치가 거기 있다. 다만 그 문법은 QueryDSL로 표현할 수 없어
`docs/rules/style.md`의 「쿼리 문자열 직접 작성은 지양」 예외가 된다. 그때 이유를 주석에 남긴다.

저장 시점은 **디바운스 500ms**로 통일한다. 슬라이더를 드래그할 때 요청이 수십 번 나가면 안 된다.
색상 편집은 이미 draft + "적용" 구조라 그대로 둔다.

#### 페이지별로 독립이다 — 같은 이름이어도 다른 값

같은 이름의 설정이 여러 페이지에 있어도 **서로 다른 값**이다. 화면에 같은 텍스트로 보여서 동일한
설정처럼 보이지만, 각 페이지에서 따로 설정하고 따로 저장하며 따로 움직인다.

"공유해야 하지 않나" 싶은 것들(제외 섹터 목록, 색상 임계값, 시총 구간 정의)은 **설정이 아니라
사용자 데이터**라 (A)에 있고 페이지 개념 자체가 없다. 그래서 `shared` 그룹을 따로 둘 필요가 없다.

> **기존 요구사항 하나를 의도적으로 뒤집는다.** `useMarketValueTierRange.ts`에 "두 화면 모두 배포 전
> 운영 수치와 일치해야 한다는 요구사항 때문에 상태를 분리해두면 안 됨"이라고 적혀 있다. 그 이유가
> **배포 전 검증**이라 지금은 유효하지 않다고 보고 페이지별로 가른다. 나중에 "원래 공유였는데?"가
> 나오면 버그가 아니라 이 결정이다.

#### 기본값은 코드에 남는다 — 그리고 서버가 유일한 진실이어야 한다

설정 목록과 기본값을 DB 테이블(설정 기준정보 + 사용자별 값, 이른바 EAV)로 관리하는 안을 검토했고
**택하지 않았다.** EAV의 값어치는 "코드 배포 없이 설정을 추가할 수 있다"인데, 이 앱에서는 설정을
하나 추가하면 그 값을 읽어 화면을 바꾸는 프론트 코드를 반드시 같이 고쳐야 한다. **테이블이 코드보다
먼저 갈 수 없다.** 그럼 남는 이득은 "이 설정이 뭘 의미하는지를 한 곳에 모은다"뿐인데, 그건 record
타입으로 얻으면 컴파일러가 지켜주기까지 한다. 대신 값이 전부 문자열로 뭉개지고 조회가 join+pivot이
되는 비용만 남는다. 설정 14개에 치를 값이 아니다.

기본값이 필요한 경우는 신규 가입자만이 아니다. **설정을 하나 추가할 때마다 기존 사용자 payload에는
그 키가 없다.** 전체 사용자 마이그레이션을 매번 할 수 없으므로 "없으면 기본값"은 예외가 아니라
상시 경로다.

**그 기본값을 프론트와 백엔드 양쪽에 두면 안 된다.** 오늘 겪은 버그가 정확히 그 모양이었다 — 화면
기본값은 산술평균인데 서버는 가중평균 고정이라 같은 텔레그램 메시지 안에서 이미지와 캡션이 갈렸다
(`docs/instructions-telegram-average-mode.md` 참고). 기본값을 한 곳에만 두면 그 종류의 어긋남이
구조적으로 생기지 않는다.

그래서 **서버가 기본값의 유일한 진실**이고, 비로그인·초기 로드에도 서버가 기본값을 내려준다.

#### 미결 — 렌더러는 누구 계정으로 찍는가 ★

**로그인 작업을 시작할 때 이것부터 정해야 한다.**

지금 렌더러는 IP 화이트리스트로 통과한다. 로그인이 들어오면 렌더러도 인증해야 하고, 그러면 **어느
사용자의 설정으로 그림을 그릴지**가 정해져야 한다. 텔레그램으로 나가는 이미지가 그 사람의 화면이기
때문이다.

| | 내용 | 결과 |
|---|---|---|
| 가 | 텔레그램 전용 계정을 만든다 | 설정이 명시적으로 관리됨. 그 계정으로 로그인해 조정 가능 |
| 나 | 본인 계정으로 찍는다 | 내 화면이 그대로 나감. 내가 설정을 바꾸면 텔레그램도 같이 바뀜 |
| 다 | 지금처럼 URL 파라미터로 계속 넘긴다 | 계정과 무관. 서버 프로퍼티가 기준 |

**어느 쪽이든 지금 만들어둔 URL 파라미터 구조(`avgMode`/`sectorFilter`)는 버려지지 않는다** —
계정 설정 위에 덮어쓰는 수단으로 남는다. 갈리는 것은 "기본값이 프로퍼티냐 계정 설정이냐"다.

#### 범위 밖

- **nginx `limit_req`/`limit_conn`** — 이 작업을 기다릴 이유가 없어서 **선행 작업에 포함했다.**
  지금 `infra/nginx.conf`에는 요청 제한이 한 줄도 없고, 그래서 `auth_request` 자체가 무방비다.
  로그인과 무관하게 이미 뚫려 있는 구멍이라 먼저 막는다
- **볼륨 DDoS** — 서버에서 막을 수 없다. 대역폭이 먼저 죽는다. 앞단 프록시(Cloudflare 등)가 필요한데
  지금 duckdns 도메인을 쓰고 있어 도메인 이전 얘기가 된다. 실제로 공격받으면 그때 판단한다

## 데이터 지연 감지

배경 — 왜 필요한가

화면 상단에 스냅샷 시각이 찍힌다. 정상이면 그 시각이 곧 최신 데이터 시각이다.

문제는 수집이 실패했을 때다. 예를 들어 16:10 수집이 실패했는데 어딘가 구멍이 있어서 16:05 데이터가
16:12에 발송됐다고 하자. 사용자가 그때마다 현재 시각과 화면의 시각을 대조하리라 기대할 수 없다.
정신없는 장중에는 더더욱.

그래서 화면이 스스로 "이건 지연된 데이터"라고 알려줘야 한다. 지연된 경우 시각을 빨간 텍스트로
출력하는 식으로.

구상한 구조

```
SnapshotResponse<T>
├── expectedSnapshotTime   지금쯤이면 있어야 할 시각
├── latestSnapshotTime     실제로 있는 최신 데이터 시각
└── items[]                각 item의 snapshotTime은 제거
```

프론트는 두 값을 비교해서 다르면 지연으로 표시한다. 지금은 이 판단을 할 근거 자체가 응답에 없다.

item마다 snapshotTime을 들고 있는 현재 구조는 불필요하다. 리스트가 천 건이어도 시각은 전부 같다.

선행 조건 — 공휴일 판정 (아래 항목)

공휴일 판정 없이 켜면 공휴일마다 "지연됐다"고 오탐이 난다. `expectedSnapshotTime()`이 "오늘도 장이
선다"고 가정하고 계산하기 때문이다. 그래서 이건 있으면 좋은 게 아니라 진짜 선행 조건이다.

관련 코드 — 지우지 말 것

`CollectionChecker`와 `CollectionScheduler.isHoliday()`는 이 기능을 위해 미리 만들어둔 것이다.
지금은 유명무실한 상태지만 나중에 그대로 쓸 코드라 삭제하지 않는다. 지웠다 다시 살리는 게 더
번거롭다.

프론트 작업도 함께 필요하다. 응답 구조가 바뀌므로 백엔드만으로 끝나지 않는다.

## 카테고리 재배정 이력 로그

**배경**: 카테고리별 등락률의 "직전 대비 급변"을 보여주려면 두 시점의 값을 비교해야 하는데, 그 사이에
종목이 A 카테고리에서 B로 재배정되면 델타가 순수 가격변동이 아니라 구성 변경까지 섞인 값이 된다.

**확정한 설계**: `market_map_stock_category` 재배정 이력을 append-only 로그로 남긴다.
`reassign()`이 호출될 때마다 `(stock_code, category_id_from, category_id_to, changed_at)`을 기록한다.
삭제·수정 없는 순수 append.

- "구성이 바뀌었나"는 그 구간에 이벤트가 몇 번 찍혔는지가 아니라, 각 종목의 T1 시점 카테고리 vs
  T2 시점 카테고리를 직접 비교해서 판단한다(각각 그 시점 이전 마지막 이벤트의 `category_id_to`).
  이래야 "무엇이 바뀌었는지" 목록까지 같은 쿼리에서 나온다
- 어드민 화면의 실행취소/다시실행과 완전히 독립적이다. undo/redo도 평범한 `reassign` 호출이라
  이력에 남지만 "시작-끝 상태만 비교"하는 방식이라 A→B→A 왕복은 자동으로 "안 바뀜"으로 정리된다.
  undo/redo 쪽 코드를 손댈 필요가 없다

**접은 선택지**: 구성원 지문(fingerprint) 해시를 시점별로 저장해 비교하는 안. "바뀜/안바뀜"은 알 수
있어도 무엇이 바뀌었는지를 알 수 없어서 폐기했다.

**빨리 시작할수록 유리하다**: 이 로그는 기능 출시와 무관하게 미리 쌓기 시작할 수 있고, 그래야
나중에 붙일 때 "로그 시작 이전 구간은 추적 불가"라는 손실이 없다.

## Flyway — 유지 결정, 과도기 운영 방식, 릴리즈 전환

### 걷어낼지 고민했고, 유지하기로 했다

지금 Flyway가 일을 안 하면서 비용만 내고 있는 건 사실이다. `V1__create_schema.sql`을 계속
고쳐쓰는 방식에서는:

- 자동 적용을 안 한다: 이미 "적용됨"으로 기록돼 있어서 DDL은 손으로 쳐야 한다
- 이력 추적이 없다: 버전이 하나뿐이다
- 기존 데이터 보호는 `ddl-auto=validate`가 하는 일이지 Flyway가 하는 게 아니다
- 남는 건 checksum 검증뿐이고 그게 하는 일은 앱 기동을 막는 것이다

그래도 유지한다. 걷어내면 갈 곳이 둘뿐인데 모두 지금보다 나쁘다.

- `ddl-auto=update`: 실제 데이터가 있는 상태에서 Hibernate가 스키마를 자동 변경하게 두는 것.
  컬럼 삭제는 안 하면서 타입은 예측 불가하게 바꾼다. "지금 DB가 어떤 상태인지"를 알 수 없게 된다
- 완전 수동 DDL: 새 환경 구축과 스키마 추적이 불가능해진다

그리고 릴리즈 브랜치 운용을 시작하면 Flyway가 제 역할을 하게 된다. 지금은 과도기라 어정쩡한 것뿐이다.

### 수동 작업을 줄이는 방법 (미적용)

`FlywayMigrationStrategy`로 기동 시 `repair()` 후 `migrate()`를 실행하면, V1을 고쳐도 checksum이
자동으로 맞춰진다. 히스토리 테이블을 손으로 UPDATE할 일이 없어진다.

```java
@Bean
FlywayMigrationStrategy repairThenMigrate() {
    return flyway -> { flyway.repair(); flyway.migrate(); };
}
```

**대가**: `repair`를 자동으로 돌리면 "V1이 의도치 않게 바뀐 것"도 조용히 승인한다. 안전장치가 하나
없어진다. 다만 여기선 V1을 일부러 고치는 게 정책이라, 그 안전장치가 이미 방해물 역할만 하고 있다.

### 과도기 운영 플로우 (새 테이블을 추가할 때)

`V1`에 직접 맞추려 하지 말고 `V2`로 먼저 진행한다. 그게 훨씬 덜 짜증난다.

```
① V2__xxx.sql 로 새 테이블 작성 → 배포 → Flyway가 자동 적용
② 문제 없음 확인
③ V2 내용을 V1에 병합하고 V2 파일 삭제 → 배포
     · V1 checksum 불일치  → repair 적용 시 자동 처리 (미적용이면 수동)
     · V2 기록이 히스토리에 남음 → DELETE 한 줄 (수동)
④ 그 스키마를 쓰는 비즈니스 로직 배포
```

③④의 순서가 중요하다. `docs/rules/process.md`의 "마이그레이션 선-머지" 규칙과 같은 이유다.

### 릴리즈 브랜치 전환 (이 방식의 종료 시점)

가입(로그인) 기능 + 신규 기능 한두 개를 더 추가한 뒤 릴리즈 브랜치 운용을 시작할 계획이다.
그 시점부터 V1 병합을 그만둔다.

- 이후로는 큰 기능 단위 또는 기간 단위로 릴리즈 브랜치를 만든다
- 릴리즈 브랜치 개수 = Flyway 스크립트 개수
- 개발 중 생기는 자잘한 수정을 매번 새 버전으로 쪼개는 대신, 릴리즈를 실제로 배포하는 시점마다
  그때까지의 변경을 묶어 버전을 확정한다

"스크립트가 3자리수가 되는 것"에 대한 우려는 이 방식에서는 성립하지 않는다. 릴리즈당 1개면 연
10~20개 수준이고 3자리수가 되려면 몇 년이 걸린다. 폭증 우려는 개발 중 변경을 매번 쪼갤 때의
이야기다.

## JPA Auditing 전환 (검토 후 보류)

엔티티가 `createdAt` / `updatedAt`을 직접 대입하고 있다. `this.updatedAt = LocalDateTime.now(...)`
형태가 엔티티 20개에 걸쳐 51곳이다.

`@EnableJpaAuditing` + `@EntityListeners(AuditingEntityListener.class)` + `@CreatedDate` /
`@LastModifiedDate`로 바꾸면 51줄이 사라지고 "특정 메서드에서 갱신 누락" 버그가 구조적으로 막힌다.
KST 기준을 유지해야 하므로 `DateTimeProvider` 빈을 만들고
`@EnableJpaAuditing(dateTimeProviderRef = "...")`로 지정해야 한다.

왜 미뤘나 — 검증이 불가능해서다.

스키마상 `created_at` / `updated_at`이 전부 `NOT NULL`이다. 엔티티 20개 중 하나라도
`@EntityListeners`를 빠뜨리고 수동 대입만 지우면, 그 엔티티의 INSERT가 프로덕션에서 제약 위반으로
터진다. 그런데 CI에 DB가 없고 테스트 정책이 "프레임워크가 보장하는 것(JPA 매핑)은 테스트하지 않는다"라
이 실수를 잡을 자동 검증이 하나도 없다.

"정리" 작업으로 분류했었지만 실제로는 동작 변경이다. 사용자가 코드를 읽지 않는 상태에서, 검증
수단 없이 20개 엔티티의 타임스탬프 동작을 한 번에 바꾸는 건 위험 대비 이득이 작다.

하게 된다면 필요한 것
- `domain/access`의 `AllowedIp`, `AdminToken` 포함 여부 결정(로그인 작업으로 대체될 영역)
- 엔티티별 `@EntityListeners` 부착 여부를 표로 검증
- DB를 띄우는 통합 테스트 한 개라도 있어야 안전하다

## `market_map_category_change_rate_snapshot`에 `snapshot_time` 인덱스 (검토 후 보류)

이 테이블에 `snapshot_time` 단독 인덱스가 없다. UK가
`(market_type, category_id, market_value_tier_id, snapshot_time)`이라 선두 컬럼이 아니어서,
정리 배치가 매일 풀스캔한다.

**왜 미뤘나**: 인덱스를 추가하려면 `V1__create_schema.sql`을 고쳐야 하고 그러면 운영 DB에서
checksum 불일치 대응 절차를 밟아야 한다(`docs/operations.md`). 얻는 건 새벽 배치 속도뿐이라 지금은
그 비용을 치르지 않는다. 배치가 실제로 오래 걸리는 게 보이면 그때 한다.

## 대량 insert 성능 개선 (검토 후 보류)

`IndexContributionRankingCollector`가 종목당 `save()`를 호출해 5분마다 약 5,600번의 개별 INSERT가
발생한다. PK가 `GENERATED ALWAYS AS IDENTITY`라 Hibernate 배치가 구조적으로 불가능하다
(INSERT를 실행해야 번호가 나오므로 한 건씩 보낼 수밖에 없다).

**왜 미뤘나**: 초당 20건 수준이라 장애로 이어지지 않는다. 수집 한 사이클이 1~3초 더 걸리는 정도다.
반면 해결하려면 PK를 시퀀스로 바꾸는 마이그레이션이 필요하고 마이그레이션 규칙(선-머지 2단계)을
밟아야 해서 절차가 무겁다. 얻는 것 대비 비용이 크다고 판단했다.

**하게 된다면**: PK를 시퀀스 방식으로 변경(마이그레이션 필요, 이후 모든 대량 저장이 개선됨) 또는
이 경로만 JdbcTemplate 벌크 insert(마이그레이션 불필요).

**왜 미뤘나**: 프론트 워크플로 · 백엔드 워크플로 · nginx Dockerfile 3곳을 고쳐야 해서, 급한 불만 끄고
미뤘다.

## 장 종가는 15:30이 아니라 15:35 스냅샷이다 — 보존 시각을 둘로 늘린다

**아래 「실삭제로 전환한다」의 선행 조건이다.** 지금 정리 배치는 15:30만 남기고 지우도록 되어 있는데,
**그 시각은 종가가 아니다.** 실삭제로 먼저 전환했으면 매일 진짜 종가를 지우고 있었을 것이다.

### 어떻게 확인했나

키움의 `flu_rt`는 `(현재가 − 전일종가) / 전일종가`다. 뒤집으면 전일 종가가 나온다.

```
전일종가 = 현재가 ÷ (1 + flu_rt/100)
```

다음 영업일 첫 장중 스냅샷에서 이렇게 역산하면 **키움이 종가로 치는 값**이 나온다. 그것을 전 영업일의
15:25~15:45 스냅샷과 대조해 일치율을 봤다(주권만, 오차 허용 0.05% — 등락률이 소수점 둘째 자리까지만
와서 생기는 역산 오차 약 0.005%를 덮되 호가 한 틱보다는 훨씬 작은 값).

| 날짜 | 15:25 | 15:30 | 15:35 | 15:40 | 15:45 |
|---|---|---|---|---|---|
| 08-27 | 33.2 | 99.5 | (없음) | 87.7 | 85.5 |
| 08-28 | 35.0 | 99.5 | 99.8 | 86.6 | 84.0 |
| 08-31 | 31.4 | 99.6 | 99.8 | 86.2 | 83.4 |
| 09-01 | 31.7 | 99.5 | 99.9 | 86.9 | 83.9 |
| 09-02 | 29.8 | 99.3 | 99.9 | 86.0 | 83.2 |
| 09-03 | 30.1 | 99.4 | 99.9 | 87.9 | 84.2 |
| 09-04 | 32.5 | 99.7 | 99.7 | 87.6 | 84.2 |
| 09-07 | 33.2 | 99.7 | 99.9 | 86.2 | 84.0 |
| 09-08 | 31.3 | 99.6 | 99.9 | 87.0 | 82.2 |
| 09-09 | 35.5 | 99.7 | 99.8 | 87.1 | 83.9 |
| 09-10 | 29.8 | **98.1** | 99.8 | 84.6 | 82.3 |
| 09-11 | 32.1 | 99.6 | 99.8 | 87.3 | 84.3 |
| 09-14 | 30.3 | 99.6 | **100.0** | 87.2 | 84.4 |

13영업일 전부 **15:35가 최고**다. 단 하루도 15:30이 이기지 못했다.

읽히는 것이 셋이다.

- **15:20~15:30은 종가 단일가(동시호가)** 구간이라 체결이 없다. 그래서 15:25가 30%대에 머문다.
  실제로 15:20과 15:25의 일치 건수가 완전히 같았다
- **15:30에 이미 99% 이상 반영된다.** 걱정했던 "2~3분 지연"은 매일 10~50종목에만 해당한다.
  다만 9/10처럼 98.1%까지 떨어지는 날이 있어 편차는 15:30 쪽이 크다
- **15:40부터 오염된다.** 84~88%로 떨어지는 것은 그때부터 시간외 거래가 붙기 때문이다.
  바꿔 말하면 **15:35까지는 시간외 거래가 시작되지 않는다**

**이 셋은 전부 거래소 시간표로 설명된다.** NXT 메인마켓이 15:20에 끝나고 애프터마켓이 15:40에
시작하므로 **15:20~15:40은 NXT가 닫혀 있다.** 그 구간의 SOR은 구조적으로 KRX 단독 가격이고, KRX
종가는 15:30 동시호가로 확정된다. 그래서 15:35가 100%인 것은 우연이 아니다. 자세한 시간표는 아래
「시간외 구간 등락률」의 「전제 1」에 있다.

15:35도 100%는 아니다(99.7~100.0). 매일 3~8종목이 안 맞는다. 정리매매·거래정지 같은 특수 종목으로
보이는데 파봐야 얻을 것이 없어 숫자만 남긴다.

### 조치 — 시각을 박지 않고 종가 윈도우의 latest를 남긴다

> 한때 "15:30과 15:35 둘을 남긴다"로 적어뒀다. **바꿨다**(사용자 제안). 시각 목록을 박는 대신
> 아래 「시간외 등락률 구현 설계」의 **기준가 규칙을 그대로 쓴다.**

```
남길 행 = 그 날짜·그 마켓에서 snapshot_time이 [15:30, 15:40) 안인 것 중 가장 늦은 것
```

**8/27에 15:35 스냅샷이 아예 없다.** 그런 날 15:35 하나만 고정으로 남기는 로직이면 하루치가 통째로
사라진다. 윈도우 규칙은 그 자리에서 15:30을 잡아준다 — "없으면 15:30" 같은 폴백 목록이 필요 없다.

시각 목록보다 나은 점이 셋이다.

1. **수집 주기가 바뀌어도 안 깨진다.** `collect.interval-minutes`가 바뀌면 15:30·15:35라는 시각
   자체가 사라질 수 있다
2. **기준가와 같은 행을 남긴다.** 시간외 등락률이 기준가로 쓰는 행과 정리 배치가 보존하는 행이
   정의상 같아진다. 둘을 따로 정의하면 언젠가 어긋난다
3. **아래 「과거 날짜 조회」의 우선순위 규칙이 사라진다.** 거기 "15:35 우선, 없으면 15:30"이라고
   적어뒀는데, 애초에 하루에 한 행만 남으면 고를 것이 없다

보존량도 하루 2개에서 1개로 준다.

#### 주의 셋

**마켓별로 따로 판정한다.** `IndexContributionRankingCollector.collect`가 마켓마다 별도 트랜잭션을
돌려서 KOSPI만 성공하고 KOSDAQ은 실패할 수 있다. 날짜 단위로만 latest를 잡으면 그런 날 한쪽
마켓의 종가가 삭제된다.

**윈도우가 빈 날은 그날이 통째로 사라진다.** 8/27이 그렇다. 종가 행이 없으니 어차피 「과거 날짜
조회」로 그릴 수도 없어 받아들일 만하지만, **배치 로그에 "그 날짜는 보존할 행이 없었다"를 남긴다.**
나중에 달력에서 그날이 비어 있는 이유를 찾느라 헤매지 않도록.

**프로퍼티를 바꾸면 삭제 정책이 같이 바뀐다.** `market.close-window-start` / `market.after-hours-start`를
공유하므로, 그 값을 옮기는 순간 보존 대상 행도 옮겨간다. 되돌릴 수 없는 쪽이라 값을 건드릴 때
이 문서를 다시 본다.

#### 변경 범위

private static final LocalTime MARKET_CLOSE_TIME = LocalTime.of(15, 30);

지금 `targetPredicate`는 `hour/minute`가 이 상수와 다른 행을 지운다. 이것을 "(날짜, 마켓)별 윈도우

### 재현 쿼리

보존 시각을 다시 의심하게 되면 이걸 그대로 돌린다. 날짜 창만 바꾸면 된다.

```sql
WITH ord AS (
  SELECT stock_code FROM stock_info
  WHERE active = true AND market_code IN ('0','10')
),
days AS (
  SELECT d, LEAD(d) OVER (ORDER BY d) AS next_d
  FROM (SELECT DISTINCT snapshot_time::date AS d
        FROM sector_price_snapshot
        WHERE snapshot_time >= CURRENT_DATE - 30) x
),
ref AS (                       -- 각 영업일의 "다음 영업일 첫 장중 스냅샷" 시각
  SELECT dy.d, MIN(s.snapshot_time) AS ref_time
  FROM days dy
  JOIN sector_price_snapshot s
    ON s.snapshot_time >= dy.next_d + TIME '09:30'
   AND s.snapshot_time <  dy.next_d + TIME '15:00'
  WHERE dy.next_d IS NOT NULL
  GROUP BY dy.d
),
real_close AS (                -- 그 시각 등락률에서 전일 종가를 역산
  SELECT r.d, s.stock_code,
         s.current_price / (1 + s.change_rate / 100.0) AS close_price
  FROM ref r
  JOIN sector_price_snapshot s ON s.snapshot_time = r.ref_time
  WHERE s.change_rate > -100 AND s.current_price > 0
),
candidate AS (
  SELECT s.snapshot_time::date AS d, s.snapshot_time::time AS t,
         s.stock_code, s.current_price
  FROM sector_price_snapshot s
  WHERE s.snapshot_time >= CURRENT_DATE - 30
    AND s.snapshot_time::time BETWEEN TIME '15:25' AND TIME '15:45'
    AND s.current_price > 0
),
matched AS (
  SELECT c.d, c.t,
         abs(c.current_price - r.close_price) / r.close_price < 0.0005 AS ok
  FROM candidate c
  JOIN real_close r ON r.d = c.d AND r.stock_code = c.stock_code
  JOIN ord        ON ord.stock_code = c.stock_code
)
SELECT d AS 날짜,
       ROUND(100.0*count(*) FILTER (WHERE t=TIME '15:25' AND ok)/NULLIF(count(*) FILTER (WHERE t=TIME '15:25'),0),1) AS "15:25",
       ROUND(100.0*count(*) FILTER (WHERE t=TIME '15:30' AND ok)/NULLIF(count(*) FILTER (WHERE t=TIME '15:30'),0),1) AS "15:30",
       ROUND(100.0*count(*) FILTER (WHERE t=TIME '15:35' AND ok)/NULLIF(count(*) FILTER (WHERE t=TIME '15:35'),0),1) AS "15:35",
       ROUND(100.0*count(*) FILTER (WHERE t=TIME '15:40' AND ok)/NULLIF(count(*) FILTER (WHERE t=TIME '15:40'),0),1) AS "15:40",
       ROUND(100.0*count(*) FILTER (WHERE t=TIME '15:45' AND ok)/NULLIF(count(*) FILTER (WHERE t=TIME '15:45'),0),1) AS "15:45"
FROM matched
GROUP BY d ORDER BY d;
```

## 스냅샷 정리를 실삭제로 전환한다

**선행 조건**: 위 「장 종가는 15:35 스냅샷이다」가 먼저다. 보존 시각을 고치기 전에 실삭제로 전환하면
진짜 종가를 지운다.

`market-monitor.retention.dry-run`이 아직 `true`다. 배치는 매일 돌지만 아무것도 지우지 않는다.

**막혀 있던 이유는 드라이런 로그가 아무것도 증명하지 못했기 때문이다.** 판정 기준은 "삭제 대상
건수가 cutoff 이전 전체 건수의 대부분일 것"인데, 두 값이 똑같이 나왔다. 확인해보니 cutoff
(30일 전) 이전에는 15:30 스냅샷이 한 건도 없었다. 5분 간격 수집을 시작한 것이 `ca2cde9`
(2026-08-26)라 아직 30일이 안 됐기 때문이다. 남길 것이 애초에 없으니 "전부 삭제 대상"이 나온
것이고, 술어가 뒤집혀 있어도 같은 숫자가 나온다.

### 보존 기간을 10일로 줄였다 (PR #107, 완료)

기다리는 대신 기간을 줄였다. 한 달을 못 채우고도 데이터가 기가 단위를 바라보는데 월 단위로 들고
있을 이유가 없다는 판단이다. `SnapshotRetentionScheduler.RETENTION_DAYS`가 10이다.

10일이면 cutoff 이전 구간에 15:30 스냅샷이 존재한다. 그래서 **대상 건수 < cutoff 이전 전체 건수**가
성립하고, 기다리지 않고 술어를 판정할 수 있다.

`dry-run`은 프로퍼티지만 `RETENTION_DAYS`는 자바 상수다. 다시 바꾸려면 배포가 필요하고, "10일"이
적힌 주석과 테스트 이름·기대 날짜도 같이 어긋난다.

**기간을 줄여도 첫 실삭제에서 지울 양은 줄지 않는다.** 오히려 늘어난다. 아래 초기 정리 SQL은 그대로
필요하다.

### 남은 순서

**배치는 KST 04:00에 돈다.** 배포한 다음날 아침부터 드라이런 로그를 읽을 수 있다.

1. 드라이런 로그로 판정 (대상 건수 < cutoff 이전 전체, 시각 표본에 `15:30`이 없을 것)
2. **초기 정리 SQL 수동 실행.** 배치는 `cutoff`보다 오래된 것을 **한 문장으로 전부** 지운다.
   정상 운영에서는 그게 하루치라 문제가 없지만, 지금은 쌓여 있는 전체가 한 번에 걸린다. 단일
   DELETE는 락과 테이블 팽창을 부른다
   - `sector_price_snapshot`은 청크 삭제. `snapshot_time` 인덱스가 있어 청크 반복이 싸다.
     한 번에 5만 행씩, 0행이 나올 때까지 반복. 멱등이어야 한다
   - `market_map_category_change_rate_snapshot`은 `snapshot_time` 인덱스가 **없어서** 청크마다
     풀스캔이 된다. 쪼개면 손해다 — 단일 문으로
   - 끝나고 `VACUUM (ANALYZE)`. 대량 DELETE 후 공간이 회수되지 않는다
   - 실행은 `docker exec -it market-monitor-postgres psql -U market_monitor -d market_monitor_db`
3. `~/env/market-monitor.env`에 환경변수를 넣고 컨테이너 재기동 →
   `MARKET_MONITOR_RETENTION_DRY_RUN=false`
4. 다음날 로그에 삭제 완료가 찍히는지 확인
5. 그다음 아래 「드라이런 경로 제거」

## 스냅샷 정리 배치의 드라이런 경로 제거

`market-monitor.retention.dry-run`은 술어가 뒤집혔는지 한 번 확인하려고 만든 장치다. 삭제 술어는
QueryDSL이 만드는 쿼리가 결정하는데 이 프로젝트에 DB 테스트가 없어서, 술어가 반대로 뒤집혀
있어도 컴파일과 단위 테스트가 전부 통과한다. 그래서 사람이 로그를 한 번 읽고 판정하는 경로를
뒀다.

검증이 끝나 실삭제로 전환하면 다시 `true`가 될 일이 없다. **위 항목이 끝난 뒤에 걷어낸다.**
지우는 범위는 `if (dryRun) return;` 한 줄이 아니라 드라이런 로그를 위해서만 존재하는 조회 경로
전체다.

- `dry-run` 프로퍼티와 `@Value`
- 두 리포지토리의 `summarizeSnapshotsToDelete()`와 `SnapshotRetentionSummary`
- Custom 인터페이스의 선언 두 곳과 관련 테스트

대략 120줄이다. 실삭제 경로는 이미 삭제 건수를 따로 찍고 있어서 운영에 지장이 없다.

제대로 된 대안은 DB를 띄우는 통합 테스트로 술어를 검증하는 것이다. 그러면 CI가 증명하므로 이
장치가 처음부터 필요 없다. 지금 이 프로젝트에는 DB 테스트가 한 건도 없어서 도입 비용이 커
택하지 않았다. 나중에 통합 테스트를 들이게 되면 이 항목은 자연히 해소된다.

보존 정책을 바꿀 때(30일을 60일로 등) 같은 검증이 다시 필요해지는데, 그때는 세 줄짜리 플래그를
다시 넣으면 된다.

## 랭킹 규칙이 프론트와 백엔드에 따로 있다

"대분류(부모 없는 카테고리)만 고른다, 기본 제외 구간을 뺀다, TOP3를 자른다"는 규칙이 두 곳에
각각 구현되어 있다. 화면은 프론트가, 텔레그램 텍스트는 백엔드
(`CategoryRankingTextBuilder`, 5단계 이후로는 `domain/view`)가 계산한다.

텔레그램은 프론트가 그린 이미지와 백엔드가 만든 텍스트를 한 메시지로 붙여 보낸다. 두 규칙이
어긋나면 같은 메시지 안에서 이미지와 텍스트가 다른 순위를 말하게 된다. 지금은 맞춰져 있지만
유지가 사람 손에 달려 있고, 한쪽만 고치면 조용히 갈라진다. 코드에도 "화면도 같은 기준으로
매기므로 텍스트도 맞춘다"는 주석으로 그 사실이 적혀 있다.

해소하려면 백엔드가 랭킹을 확정해서 내려주고 프론트는 그리기만 해야 한다. 프론트 레포 변경과
배포가 함께 필요해서 미뤘다.

프론트엔드 레포 정비를 시작할 때 같이 본다.

## 알림 채널이 텔레그램 하나뿐이다

장애 알림이 `EscalationPublisher` → `EscalationNotifier` → 텔레그램 한 경로로만 나간다. 텔레그램이
통째로 죽으면 알림이 전달되지 않고 `exception.log`만 남는다. 파일은 서버에 들어가야 보이므로
사실상 알림이 없는 것과 같다.

`TelegramClient`가 실패했을 때도 마찬가지다. `EscalationNotifier`가 예외를 잡아 로그만 남기므로
순환은 생기지 않지만, 알림을 보내야 할 상황에서 알림 수단이 그 상황의 원인이라는 구조는 그대로다.

실제로 겪는 실패는 대부분 부분 실패(이미지 크기 초과, 타임아웃, rate limit)라 알림 자체는 나간다.
전체 장애일 때만 못 간다. 그래서 급하지 않다.

풀려면 두 번째 경로가 필요하다. 이메일이든 외부 로그 수집이든 상관없지만, 텔레그램에 의존하지 않는
경로여야 한다. 5단계에서 `TelegramClient`의 예외 타입을 바꿔도 이 문제는 그대로 남는다.

## 텔레그램 경로가 before를 조회하고 버린다

`CategoryRankingTextBuilder`가 만드는 캡션은 `item.now()`만 쓴다. 그런데 그 값을 만들어주는
`MarketMapQueryService.getTopCategoryRankings`는 `findRankingForMarkets`를 타고, 거기서 before
시각 조회가 무조건 한 번 더 돈다.

```java
// MarketMapCategoryChangeRateSnapshotService.findRankingForMarkets
Map<Market, Map<Long, List<CategoryTierBreakdown>>> nowByMarket =
        findTierBreakdownsByCategoryId(markets, snapshotTime);
Map<Market, Map<Long, List<CategoryTierBreakdown>>> beforeByMarket =
        findTierBreakdownsByCategoryId(markets, beforeTime);   // 텍스트는 이걸 안 쓴다
```

`findTierBreakdownsByCategoryId` 한 번이 리포지토리 호출 두 건이다 —
`marketValueTierThresholdRepository.findAll()`과
`findByMarketTypeInAndSnapshotTime(markets, snapshotTime)`. 뒤쪽은 카테고리 × 구간 × 마켓 수만큼
행이 나온다.

「섹터 "변화율" 그래프에 마켓 지수 바를 넣는다」가 들어가면 여기에 `market_overview_snapshot`
before 조회가 한 건 더 붙는다. 그쪽은 스냅샷 시각당 두 행짜리라 작지만, 버리는 조회가 늘어나는
방향인 것은 같다.

### 규모

발송 한 번에 `getTopCategoryRankings`를 한 번 부르는데, 맵 포함 tick은 마켓별로 나뉘어 두 번이다.

```
WITH_MAP     7회 × 2 = 14
SECTOR_ONLY  42회 × 1 = 42
             하루 56회
```

하루 56번 조회하고 버린다. 장애로 이어질 규모는 아니다.

### 구조 — 시각 하나짜리 조립을 만들고 화면이 그걸 두 번 쓴다

시각 하나로 조회하는 부분(`findTierBreakdownsByCategoryId`)은 이미 갈라져 있다. 갈라야 하는 것은
그 위에서 now/before를 짝짓는 **조립 층**이다.

```
findTierBreakdownsByCategoryId(markets, 시각)      ← 공통. 지금도 public이다
  ├─ 텍스트  시각 한 번 → CategoryChangeRateItem.withoutBefore
  └─ 화면    시각 두 번(now, before) → 짝지어 CategoryChangeRateItem
```

`CategoryChangeRateItem.withoutBefore` 팩터리가 이미 있어서 텍스트 쪽 조립에 그대로 쓴다. 지수
등락률도 같은 모양으로 갈린다 — 텍스트는 now 하나, 화면은 `MarketIndexChangeRate(now, before)`.

**갈라야 하는 것은 "시각을 몇 개 조회하느냐"뿐이다.** 카테고리 이름·depth를 붙이는 것, 대분류만
고르는 것, 기본 제외 구간을 빼는 것, TOP3를 자르는 것은 **한 곳에 그대로 둔다.** 5단계 5-3이
그걸 한 곳으로 모으느라 한 작업이라, 여기서 되쪼개면 같은 규칙이 다시 두 벌이 된다. 그때
접었던 선택지로 돌아가는 것이다.

### 선행 조건 — 지수 before 작업 이후

지수 before가 `getCategoryChangeRates`의 조회 구성을 한 번 더 바꾼다. 그게 끝난 뒤에 해야 무엇을
몇 갈래로 가를지가 확정된다. 같은 파일을 동시에 건드리지 않는 이유도 있다.

### 왜 지금 안 하나

얻는 것이 하루 56번의 작은 조회다. 반면 5-3이 통합한 경로를 손대는 작업이라, 잘못하면 랭킹 규칙이
다시 두 벌이 된다. 지금은 그 위험이 이득보다 크다.

성능보다 **의미가 드러난다**는 쪽이 실은 더 큰 이유가 된다. 지금은 `toCategoryRankingSummary`를
읽어도 before가 필요한지 아닌지 알 수 없다. 타입이 "이 경로는 now만 쓴다"를 말해주면 그 확인이
필요 없어진다. 그래서 성능 때문이 아니라 구조를 정리할 때 함께 하면 된다.

## 시간외 구간 등락률

정규장이 끝난 뒤에도 가격은 움직이는데, 화면의 등락률은 **전일 종가 기준** 그대로다. 그래서
"장 끝나고 이 종목이 얼마나 움직였나"를 볼 방법이 없다. 15:35(종가)를 새 기준선으로 삼는 등락률을
따로 보여주자는 것이다.

```
시간외 등락률 = (현재가 − 그날 15:35 가격) ÷ 그날 15:35 가격 × 100
```

### 전제 1 — 거래소 운영 시간. 여기부터 읽어야 한다

숫자 해석이 전부 이 시간표 위에 서 있다. 2026-09-15에 NEXTRADE 홈페이지와 언론 보도로 확인했다.

```
NXT   프리마켓    08:00~08:50   591 종목
      메인마켓    09:00:30~15:20  604 종목      ← 15:20에 끝난다. KRX보다 10분 이르다
      애프터마켓  15:40~20:00   602 종목

KRX   정규장      09:00~15:30
      프리마켓    07:00~07:50   ┐ 2026-09-14 신설
      애프터마켓  16:00~20:00   ┘ 실시간 거래. ETF·ETN과 일부 관리종목 제외, 시장가 주문 불가
```

**KRX 애프터마켓 시행일이 2026-09-14다.** 기존 시간외 단일가(16:00~18:00)는 없어졌다. 아래 근거 표의
마지막 날이 하필 그 첫날이라, 9/14 데이터는 이전 날들과 성격이 다르다.

- [9월14일부터 바뀌는 시간외거래 (한국경제)](https://www.hankyung.com/article/202609043639i)
- [2026 KRX 애프터마켓 거래방법](https://www.make2t.kr/2026/09/krx-after-market-trading.html)

이 시간표에서 따라오는 것들이다.

- **15:20~15:40은 NXT가 닫혀 있다.** NXT 메인마켓이 15:20에 끝나고 애프터마켓이 15:40에 시작하기
  때문이다. 그래서 **그 구간의 SOR은 구조적으로 KRX 단독 가격이다.** 15:35 스냅샷이 KRX 종가와
  100% 일치하는 것이 우연이 아니라 필연이다
- **15:40~16:00은 NXT 602종목만** 움직인다. 근거 표의 15:40이 87%(약 356종목 불일치)인 것과 규모가
  맞는다
- **16:00부터는 사실상 전 종목**이 움직인다. 9/14의 19:00 시점에 주권 2,739 중 2,161(78.9%)이
  15:30과 달랐던 것이 이것으로 설명된다. KRX 애프터마켓 첫날이었다
- **`collect.start-hour=8`이라 KRX 프리마켓(07:00~07:50)이 통째로 수집 범위 밖이다.** 아래
  「KRX 프리마켓이 수집 범위 밖이다」 참고

**검증 가능한 예측**: 날짜별로 "15:35 대비 가격이 바뀐 종목 수"를 시각대별로 세면, 9/11 이전 19:30은
600 언저리, 9/14부터 2,000대로 뛰어야 한다. 아직 안 돌려봤다.

### 전제 2 — SOR의 성질

이 항목의 판단은 전부 아래 사실 위에 서 있다. 코드만 봐서는 안 보이고 DB를 봐야 나온다.

**`ka20002`를 `stex_tp=3`(KRX+NXT)으로 부르면 응답은 SOR 행 하나로 온다.** 종목코드에 `_AL`
suffix가 붙는다. KRX와 NXT 중 유리한 쪽 호가를 알아서 물어다 주는 통합 가격이다.

그래서 이런 것들이 따라온다.

- **`sector_price_snapshot.exchange_type`은 전 행이 `SOR`이다.** 정보량이 0이다
- **`ExchangeType.KRX`/`NXT` 분기는 죽은 코드다.** `IndexContributionRankingCollector`의
  "종목당 KRX 줄을 우선 채택" 규칙(`isKrx()`)은 한 번도 참이 된 적이 없다
- **어느 거래소 가격인지 시간으로 추론할 수 있는 구간은 하나뿐이다.** NXT가 정규장 시간에도 열려
  있어서 10:00 스냅샷의 SOR 값은 출처가 미상이고, 16:00 이후는 KRX 애프터마켓까지 겹쳐 역시
  미상이다. 유일한 예외가 **15:20~15:40** — NXT가 닫혀 있어 KRX 단독으로 볼 수 있다.
  "15:40 이후니까 NXT겠지"는 15:40~16:00에만 참이고 16:00부터는 틀리다
- **그래도 대부분 문제가 안 된다.** SOR은 "지금 얼마에 살 수 있나"이고, 화면에 보여줄 값으로는
  오히려 이쪽이 맞다. 시간외 등락률도 분자·분모가 둘 다 SOR이라 거래소를 몰라도 성립한다

**SOR 채택은 지금도 옳은 선택이다.** KRX 단독으로 갔으면 15:30 이후 전 종목 가격이 얼어붙어
(지금 마켓 지수 바가 겪는 것과 같은 문제) 이 기능 자체가 불가능했다. 거래소를 나눠 부르는 것은
되돌릴 일이 아니라 필요해지면 **덧붙일** 일이다 — `stex_tp=2`를 하루 한 번 부르면 되고, 그것은
5분 주기 경로(하루 156 사이클)를 건드리지 않는다.

### 규모 — 기능이 성립하는가

2026-09-14 기준, 15:30 대비 19:00에 가격이 바뀐 종목 비율이다.

```
전체(ETF 포함)   4,296 중 2,178   50.7%
주권만           2,739 중 2,161   78.9%
```

**주권 기준 78.9%가 움직인다.** ETF가 희석하고 있었다 — ETF·ETN은 KRX 애프터마켓 거래 대상이
아니라 시간외에 잘 안 움직인다. 화면에서 이미 걸러내고 있어 기능에는 영향이 없다.

단 **9/14는 KRX 애프터마켓 첫날**이라 이 78.9%는 새 제도 기준 숫자다. 그 이전 날들로 재면 훨씬
작게 나온다(NXT 602종목만 움직였을 테니). 제도가 바뀐 뒤가 앞으로의 정상이므로 78.9% 쪽을 기준으로
본다.

(15:30 기준으로 잰 값이다. 기준선이 15:35로 확정됐으니 다시 재면 몇 종목 달라진다.)

### 기준선은 15:35 종가 하나. 종목별로 나누지 않는다

한때 "NXT 거래 종목(602개)에 한해 15:40을 시작가로 잡는" 안을 검토했다. **KRX 애프터마켓 시행으로
필요가 없어졌다.** 16시부터 사실상 전 종목이 거래되므로 종목마다 기준선을 다르게 잡을 이유가 없다.

그리고 15:40 스냅샷은 **시가가 아니다.** 5분 간격으로 찍는 값이라 장 시작 시점을 정확히 잡을 수
없고, 실제로 그 시각엔 이미 356종목쯤이 움직인 뒤다. 15:35는 13영업일로 검증된 확정값이라는 점에서도
기준선으로 낫다.

**NEXTRADE 자신도 애프터마켓 등락률에 「기준가 대비」와 「KRX종가 대비」를 나란히 표시한다.**
우리가 15:35(KRX 종가)를 기준으로 잡는 것과 같은 발상이다.

### 새 API도 새 컬럼도 필요 없다

15:35 스냅샷은 정리 배치가 영구 보존하는 행이다. 계산에 필요한 재료가 이미 다 있다.

그리고 카테고리 등락률은 이미 `now`/`before` 짝 구조다(`CategoryChangeRateItem`). **"before를 그날
15:35로 고정"** 형태면 기존 조립 로직을 거의 그대로 쓴다.

> 이 "before 고정" 안은 아래 「시간외 등락률 구현 설계」에서 **채택하지 않았다.** 카테고리 단위
> %p 델타만 나와서 지도의 개별 종목 박스가 전일 대비로 남는다. 그쪽을 먼저 읽는다.

**`stock_info`에 "NXT 거래 종목" 플래그를 다는 안은 넣지 않는다.** 기준선이 전 종목 공통이라
어느 종목이 NXT인지 알 필요가 없다.

> 이 판단은 하루 사이에 두 번 뒤집혔다. 처음엔 "78.9%면 없어도 읽힌다"로 보류했고, "NXT 종목만
> 다른 기준선"이라는 안이 나오면서 필요하다고 물렸다가, KRX 애프터마켓 시행을 확인하고 다시
> 불필요로 돌아왔다. **마지막 근거만 제도 확인이고 앞의 둘은 추측이었다.** 다시 꺼내게 되면
> 그 차이를 기억한다.

### 제약 — NXT 결과를 스냅샷 테이블에 넣으면 화면이 죽는다

```java
// SectorPriceSnapshotService.findPriceByStockCode
.collect(Collectors.toMap(SectorPriceSnapshot::getStockCode, Function.identity()))
```

`stock_code`는 suffix를 떼고 저장하는데(`005930_NX` → `005930`) UK는 `exchange_type`을 포함한다.
한 시각에 SOR 행과 NXT 행이 둘 다 들어오면 **이 `toMap`이 `Duplicate key`로 터지고 마켓맵과 섹터
페이지가 통째로 죽는다.** 지금 안 터지는 것은 종목당 한 행만 오기 때문이다.

그러므로 **거래소별 조회를 하게 되더라도 그 결과는 `sector_price_snapshot`에 넣지 않는다.**
`stock_info`의 컬럼 같은 별도 자리에 둔다.

### 마켓 지수 바가 같이 걸린다 — 실측으로 확인했다

> 여기 처음엔 "노란 마켓 지수 바는 무조건 0%가 된다"고 적어뒀다. **부정확했다.** 그대로 두면
> 0%가 아니라 **전일 대비 값이 고정으로 남는다.** 0%가 되는 것은 같은 기준(15:35 대비)으로
> 재계산했을 때다. 아래가 실측이다.

**2026-09-15 KOSPI 지수, 5분 간격 (`market_overview_snapshot`)**

```
15:20  6617.73  -1.00%   ← 종가 동시호가 구간, 15:20=15:25 동일
15:25  6617.73  -1.00%
15:30  6627.24  -0.85%   ← 동시호가 결과 반영, +9.5p 점프
15:35  6627.26  -0.85%   ← 확정
15:40  6627.26  -0.85%
  ...           (전부 동일)
20:00  6627.26  -0.85%
```

**15:35 이후 20:00까지 한 번도 안 움직인다.** 시간외 거래는 지수에 전혀 반영되지 않는다.
`ka20001`에 `stex_tp`가 없다는 것과 일치하고, 15:20~15:30이 동시호가라 지수가 멈춰 있다가
15:30에 점프하는 것도 제도와 맞는다.

**그리고 지수의 확정 시각도 15:30이 아니라 15:35다.** 종목과 같다.

다음날이 기준으로 삼는 전일 종가 지수(`index_value ÷ (1 + change_rate/100)` 역산)를 13영업일치
비교하면 15:30/15:35/16:00/20:00 전부 **0.2~0.3 이내**로 맞고 15:25만 크게 어긋난다. 이 0.2~0.3은
`flu_rt`가 소수점 2자리(0.01%)뿐이라 6,600선에서 ±0.33이 남는 **반올림 오차**다 — 그래서 이
역산으로는 15:30과 15:35(차이 0.02)를 구분할 수 없다. 구분해준 것은 위 "15:35부터 고정"이다.

**결론: 시간외 구간에는 지수라는 것이 존재하지 않는다.** 15:35 값이 그날의 마지막이고, 다음날은
그 값을 전일 종가로 삼아 출발한다. 시간외 흐름은 지수에 누적되지 않고 다음날 시초가에 간접적으로
녹아들 뿐이다.

#### 결정 — 지금은 손대지 않는다

| | 내용 | 크기 |
|---|---|---|
| 가 | 시간외 구간엔 지수 바를 **숨긴다** | 작다. 되돌리기 쉽다 |
| 나 | 아래 「마켓 지수 바의 기준이 카테고리 바와 다르다」의 전체 종목 가중평균으로 **교체** | 크다. 정규장 지수의 정의가 바뀐다 |

그때 (가)를 한다.

**알고 받아들이는 어긋남**: 15:40 이후 화면에서 노란 지수 바는 **전일 대비 값이 고정**으로 남고
(예: −0.85%) 카테고리 바는 **15:35 대비**로 0 근처에서 움직인다. 두 막대의 기준이 다르다. 나중에
"지수 바만 왜 저러냐"는 말이 나오면 버그가 아니라 이 결정이다.

### 이름은 거래소를 말하지 않는다

**"NXT 등락률"이라고 부르지 않는다.** 그렇게 부르면 거래소를 증명해야 하는데, 16시 이후 SOR 가격이
어느 거래소에서 왔는지는 알 수 없다. **"시간외 등락률"** 또는 **"장 마감 후 등락률"**이면 증명할
것이 없고, 실제로 우리가 보여주는 것("종가 이후 얼마나 움직였나")과도 정확히 맞는다.

## 시간외 등락률 구현 설계 — 등락률을 우리가 계산한다

위 「시간외 구간 등락률」을 어떻게 만들 것인가. 앞 절이 **무엇을 보여줄지**를 정했다면 여기는
**어디를 고칠지**다.

원래 앞 절에는 `CategoryChangeRateItem`의 `now`/`before` 짝에 **"before를 그날 15:35로 고정"**
하는 안을 적어뒀다. 그 방식은 저장된 등락률을 안 건드려서 싸지만, **카테고리 단위 %p 델타만
나온다.** 지도의 개별 종목 박스는 여전히 전일 대비 색으로 칠해진다. 아래 설계는 그 대신
**종목 등락률을 종목 단위로 따로 계산해서 저장한다** — 지도·섹터·텔레그램이 같은 값을 쓴다.

세 결정이 이 설계를 이룬다. **결정 1**은 그 계산을 조회 시점이 아니라 수집 시점에 한다는 것,
**결정 2**는 15:35 이전 구간은 건드리지 않는다는 것, **결정 3**은 키움 값을 덮지 않고 나란히
저장해 둘 다 볼 수 있게 한다는 것이다. 결정 3이 가장 나중에 들어와서 결정 1의 서술 일부를
바꿔놨다 — 읽는 순서대로 따라오면 된다.

### 확인한 것 — 등락률의 진입점이 하나다

수술 범위를 먼저 재봤다. 화면에 뜨는 모든 등락률은 `sector_price_snapshot.change_rate` 하나에서
나온다.

| 지점 | 무엇을 하나 |
|---|---|
| `IndexContributionRankingCollector.toSectorPriceEntity` | 키움 `flu_rt`를 그대로 `change_rate`에 **저장** |
| `MarketMapQueryService.toMarketMapItem` | 그 값을 읽어 `MarketMapItem.changeRate`로 |
| `MarketMapCategoryChangeRateSnapshotService.computeRawSums` | 그 `MarketMapItem.changeRate`로 Σ등락률×시총을 만들어 **저장** |

**중간에 다른 출처가 끼어들지 않는다.** 저장 시점의 한 줄을 바꾸면 지도 박스, 카테고리 가중평균,
섹터 페이지, 텔레그램 캡션이 전부 따라온다. 계획의 전제 중 가장 불확실했던 부분인데, 다행히 좁다.

### 결정 1 — 아무것도 저장하지 않는다. 조회 시점에 계산한다

> **이 결정은 한 번 뒤집혔다.** 처음엔 "수집 시점에 저장"으로 정했고 그 근거가 아래 「원래 왜
> 수집 시점이었나」다. 그 근거가 집계 테이블을 쓴다는 전제 위에 서 있었는데, 시간외를 그 테이블에
> 넣지 않기로 하면서 전제가 사라졌다. 읽는 순서대로 따라오면 된다.

시간외 등락률은 **DB에 한 줄도 쓰지 않는다.** 화면이 토글을 켤 때 그 자리에서 계산한다.

```
시간외 등락률 = (현재가 − 그날 15:35 가격) ÷ 그날 15:35 가격 × 100
                  ↑                ↑
              그 행에 이미 있다   종가 캐시(아래 「그래서 캐시가 작아진다」)
```

종목당 뺄셈 하나다. 지도 페이지는 **이미 그 4,300행을 읽어서** 트리를 만들고 있으므로
(`findPriceByStockCode`) 그 루프 안에서 한 줄 더 하는 것뿐이다. 카테고리 집계도 그 값으로 조회
시점에 group-by 한다.

#### 저장이 과거 조회를 풀어주지 못한다

저장하자는 안이 나왔던 이유는 "달력으로 지난 날짜의 시간외를 보려면 남겨둬야 하지 않나"였다.
**정리 배치가 그 질문의 답을 이미 정해놨다.**

```
15:35 종가 행       →  영구 보존   (정리 배치가 남기는 그 한 행)
15:40~20:00 행      →  10일 뒤 삭제 ← 시간외 값이 사는 자리
```

`after_hours_rate` 컬럼을 만들어 저장해도 **그 행 자체가 삭제된다.** 집계 테이블에 `basis`로
넣어도 같은 배치를 타므로 마찬가지다. 즉 **어떻게 저장하든 시간외 등락률은 10일짜리 데이터다.**

| | 저장한다 | 조회 시점에 계산한다 |
|---|---|---|
| 마이그레이션 | 컬럼 2개 + `basis` + UK 변경 | **없음** |
| 10일 이내 과거 | 보인다 | 보인다 (원본이 살아 있다) |
| 10일 지난 과거 | **안 보인다** | 안 보인다 |
| 구획 2에서 | 버린다 | 그대로 간다 |

10일 이내에는 현재가도 기준가도 살아 있어 계산 결과가 저장한 것과 같고, 10일이 지나면 둘 다
못 본다. **저장해서 얻는 것이 없다.**

정말 오래 보려면 방법은 하나뿐이다 — 정리 배치가 15:40 이후 행을 남기게 바꾸는 것. 그건 보존
정책 변경이고 하루 21만 행이 영구히 쌓인다. 별개 결정이라 여기서 다루지 않는다.

#### 원래 왜 수집 시점이었나 — 그 근거가 사라졌다

등락률은 **DB에 두 번, 서로 다른 모양으로 저장된다.** 5분마다 도는 수집 tick 하나가 이 둘을
연달아 쓴다.

```
키움 응답 (현재가, flu_rt)
   │
   ├─ 종목별로 sector_price_snapshot 에 저장          ← 지도 페이지가 읽는 것
   │
   └─ 카테고리별 Σ(등락률×시총) 을 계산해서
      market_map_category_change_rate_snapshot 에 저장  ← 섹터 페이지가 읽는 것
```

섹터 페이지는 **이미 다 더해진 값**을 읽는다. 종목별 등락률을 다시 더하지 않는다. 그래서 조회
시점에 종목 등락률만 바꾸면 15:40에 지도의 반도체 박스는 `+0.1%`인데 섹터 페이지의 반도체 막대는
`+2.3%`가 된다. 같은 시각, 같은 카테고리인데 숫자가 다르다 — 이것이 "수집 시점에 저장한다"의
근거였다.

**그 근거는 "집계 테이블을 쓰는 한"에서만 유효했다.** 시간외를 그 테이블에 넣지 않고 지도·섹터
둘 다 조회 시점에 조립하면 값이 갈릴 수가 없다. 같은 계산을 타기 때문이다.

덤으로 원래 있던 대가도 사라진다. 수집 시점 저장은 "잘못된 값이 들어가도 그 시각을 재수집할 방법이
없다"(`existsByMarketTypeAndSnapshotTime` 가드)는 문제를 안고 있었는데, 아무것도 안 쓰면 그 문제
자체가 없다.

#### 구획 2의 리허설이 된다

시간외 토글을 켜면 섹터 페이지가 집계 테이블 대신 종목 행을 직접 읽는다. 그것이 정확히 구획 2가
갈 길이다. 아래 「멀티테넌시 — 카테고리 집계 테이블을 없앤다」에 이렇게 적어뒀다.

> **배포 전에 재야 한다.** 위는 코드를 읽고 세운 논증이지 측정이 아니다.

시간외를 이 방식으로 만들면 **그 측정이 공짜로 된다.** 그것도 15:40~20:00이라는 트래픽 적은
구간에서다. 느려도 시간외 토글만 굼뜨고 기존 화면은 그대로다. 구획 2에서 전일 대비를 옮길 때는
이미 답을 알고 시작한다.

대가는 하나다 — **구획 2까지 두 경로가 공존한다.** 전일 대비는 미리 계산한 값을 읽고, 시간외는
조회 시점에 계산한다. 구획 2에서 하나로 합쳐진다.

### 결정 2 — 15:35 **이전**은 손대지 않는다

계획에서 한 덩어리를 덜어내자는 제안이다.

원안은 15:35 이전 구간도 "직전 거래일 15:35 가격"을 기준으로 직접 계산하자는 것이었다. 공식
하나로 통일된다는 점은 분명한 장점이다. 반대하는 이유는 둘이다.

**1. 이득이 없다.** 13영업일로 확인한 대로 15:35 가격이 곧 종가다. 그 값으로 등락률을 계산하면
키움 `flu_rt`를 **재현**할 뿐이다. 같은 숫자를 얻으려고 코드를 늘리는 셈이다.

**2. 권리락에서 어긋난다.** 액면분할·유무상증자·배당락이 있는 날, 키움 `flu_rt`의 분모는 **조정
기준가**이고 우리 캐시는 **실제 체결가**다. 5:1 액면분할을 예로 들면:

| | 전날 15:35 | 분할일 주가 | 등락률 |
|---|---|---|---|
| 키움 | 100,000 | 20,000 | 기준가를 20,000으로 조정 → **0%** |
| 우리 계산 | 100,000 | 20,000 | (20,000−100,000)÷100,000 → **−80%** |

지도에서 그 종목 박스가 새빨개지고, **가중평균이라 시총이 크면 카테고리가 통째로 폭락으로
보인다.** 실제로는 아무 일도 없었는데. 텔레그램 TOP2 랭킹도 같이 틀어진다.

> **처음에 "12월 말 배당락은 전 종목에 동시에 걸린다"고 적었다. 틀렸다.** 현금배당 배당락은
> 거래소가 기준가를 조정하지 않는다 — 주가가 자연히 빠질 뿐이라 우리 계산과 키움 값이 일치한다.
> 기준가가 조정되는 것은 액면분할·병합, 무상증자, 주식배당처럼 **주식 수가 바뀌는** 권리락뿐이다.
> (빈도는 아래 실측을 본다 — 하루 3건이었다.)

**박스 크기는 안 바뀐다.** `totalMarketValue = 현재가 × listCount`인데 `listCount`가 평일 07:00
싱크(`CollectionScheduler.syncStockInfo`)로 갱신되므로, 5:1 분할이면 가격 1/5 × 주식 수 5배라
시총이 그대로다. **망가지는 것은 색과 카테고리 가중평균, 텔레그램 랭킹이다.**

**15:40 이후만 우리가 계산하면 둘 다 사라진다.** 기준가가 **당일** 15:35라 권리락이 끼어들 하루
경계가 없고, 정규장 구간은 키움이 조정해준 값을 그대로 쓴다.

#### 원안을 안전하게 만들 수는 있다 — 그런데 그러면 원안의 장점이 사라진다

권리락은 **감지할 수 있다.** 키움이 주는 `cur_prc`와 `flu_rt`로 그쪽 기준가를 역산해
(`cur_prc ÷ (1 + flu_rt/100)`) 우리 캐시의 전날 종가와 비교하면 된다. 5:1 분할이면 400% 차이라
`flu_rt`의 소수점 2자리 반올림 오차와 절대 안 겹친다. "임계값 이상 어긋나면 키움 값을 쓴다"
한 줄이면 원안도 안전해진다.

**그런데 그 한 줄을 넣는 순간 원안의 유일한 장점이 없어진다.** 원안을 하려던 이유가 "공식
하나로 통일"이었는데, 결국 "우리 계산 / 권리락이면 키움 값"이라는 분기가 생긴다. 분기 개수로
보면 "15:40 이전은 키움 값"보다 오히려 많다. 그리고 얻는 숫자는 여전히 같다.

#### 실측 — 결정 2가 확인됐다

2026-09-15 15:35 종가로 계산한 값과 2026-09-16 09:05 키움 `flu_rt`를 **직접 맞붙였다**(주권만,
`market_code IN ('0','10')`).

```
종목수 2,737 | 일치 2,734 | 불일치 3 | 일치율 99.89%   (일치 = 소수점 둘째 자리까지)
```

**99.89%가 정확히 같은 값이다.** "우리가 계산해도 키움과 같은 숫자"는 이걸로 확인됐다 — 즉
15:35 이전을 직접 계산해서 얻는 것이 없다.

안 맞는 3건은 **전부 권리락이었다.** 키움 기준가를 역산(`현재가 ÷ (1 + flu_rt/100)`)해 전날
15:35 가격과 비교하면 이렇다.

| 종목 | 전날 15:35 | 키움 기준가 | 관계 | 우리 계산 | 키움 |
|---|---|---|---|---|---|
| 하이딥 | 783 | 1,566 | 783 × **2** (주식병합·감자) | **+149.04%** | +24.52% |
| 미트박스 | 8,290 | 2,765 | 8,290 ÷ **3**, 호가 반올림 (액면분할) | **−63.39%** | +9.76% |
| 폰드그룹 | 5,020 | 4,980 | −0.8% (유상증자·주식배당 규모) | +0.20% | +1.00% |

앞의 둘은 정확히 2배·3배라 주식 수 변경이 확실하다. 세 번째는 배율이 아니지만 호가 5원 기준
8틱이라 반올림 잡음일 수 없다.

**3건 모두 키움이 맞고 우리가 틀렸다.** 하이딥이 실제 +24.5%인데 우리 계산은 +149%, 미트박스는
실제 +9.8%인데 −63%다. 그대로 나갔으면 그 박스가 극단값으로 칠해지고 카테고리 가중평균과 텔레그램
TOP2가 같이 망가진다.

> **빈도도 과소평가했다.** 위에서 "개별 종목 월 몇 건 수준"이라고 적었는데, **하루치를 재니 3건**
> 이다(2,737개 중 0.11%). 드문 사고가 아니라 상시다. 15:35 이전을 우리가 계산하면 **매일 몇
> 종목씩** 틀린 값이 나간다.

「공휴일 판정 구현」(`isHoliday()`가 `return false`인 미구현 상태)은 **이 기능과 함께 진행하기로
했다**(사용자 결정). 위 설계에서는 기준가가 당일 15:35라 "직전 거래일"을 알 필요가 없어 선행
조건은 아니지만, 원안으로 되돌아가면 곧바로 선행 조건이 된다.

### 결정 3 — 키움 값은 그대로 두고 둘 다 볼 수 있게 한다

**요구가 바뀌었다**(사용자). 15:40부터 키움 등락률을 갈아끼우는 자동 전환이 아니라, 키움 값은
건드리지 않고 **두 기준을 오갈 수 있게** 한다.

결정 1이 아무것도 저장하지 않는 쪽으로 정리되면서 이 요구는 **저절로 만족된다.** 키움 값을 덮어쓸
일이 애초에 없기 때문이다. 스키마도, 마이그레이션도 없다.

```
change_rate    키움 flu_rt      ← DB에 있는 것. 손대지 않는다
change_value   키움 pred_pre    ← 손대지 않는다
시간외 등락률                    ← DB에 없다. 토글 켤 때 계산한다
```

기준가를 못 구한 날(윈도우가 통째로 빈 날)은 **시간외 값이 없다.** 0으로 채우지 않는다 — "안
움직였다"와 "값이 없다"가 구분되어야 한다. 그 경우 화면은 기본 기준으로만 보이면 된다.

#### 화면 — 토글이다. 새 페이지가 아니다

지도 페이지와 섹터 페이지에 기준 토글을 둔다. 새 페이지를 만들지 않는다.

- 조회 경로가 공유라 **백엔드 작업량은 어느 쪽이든 같다.** 새 페이지는 그 위에 프론트 작업이
  얹힐 뿐이다
- 지도와 섹터 **양쪽 다** 필요하므로 새 페이지라면 두 개가 된다. 각각 라우트·네비·캡처 ID·
  `RenderTarget`·설정 사이드바가 복제된다
- **쿼리 파라미터 패턴이 이미 있다.** `?market=…&beforeMinutes=…&avgMode=…&sectorFilter=…`에
  `basis=daily|afterHours` 하나를 더하면 렌더러·텔레그램이 공짜로 따라온다. 새 페이지면
  `RenderTarget`부터 새로 만들어야 한다
- 같은 화면에서 토글하면 두 값이 즉시 비교된다. 새 페이지면 탭을 오가야 한다

#### 15:40 이전에는 토글을 잠근다

장중에는 시간외 등락률이 **존재하지 않는다**(사용자 결정). 토글을 비활성으로 둔다 — 애초에 DB에
쓰는 것이 없으므로 "저장하지 않는다"는 말은 따로 필요 없고, 화면이 그 구간에 그 기준을 못 고르게
하면 된다.

"가장 최근 종가 대비"로 정의를 넓혀 종일 살려두는 안은 택하지 않았다. 장중에는 그 값이 키움
`flu_rt`와 사실상 같은데(실측 99.89%), **다른 0.11%가 전부 권리락이라 우리 값이 틀린 쪽**이기
때문이다. 위 「결정 2 — 15:35 이전은 손대지 않는다」와 같은 이유다.

토글이 켜진 채 장이 열리는 경우(전날 켜둔 세션)를 화면이 처리해야 한다. 잠글 때 기본 기준으로
되돌린다.

#### 텔레그램

어느 기준으로 보낼지는 **프로퍼티로 둔다.** 스케줄러가 부르는 배치라 값을 실어 보낼 호출자가 없고,
`telegram.before-minutes`/`telegram.average-mode`가 이미 같은 구조다. 프로퍼티 하나가 캡처 URL과
캡션 계산 양쪽에 들어간다.

기본값은 **기존대로 키움 등락률**이다. 시간외 기준으로 보내고 싶어지면 그때 값만 바꾼다.

15:40 이전 tick에서 시간외 기준이 설정돼 있으면 보낼 값이 없다. 그 구간은 기본 기준으로 폴백하고
캡션에 그 사실이 드러나야 한다 — 같은 헤더로 다른 기준 값을 보내면 안 된다.

### 그래서 캐시가 작아진다

결정 2를 받으면 캐시가 들고 있어야 할 것은 **당일 15:35 가격 하나**다. 원안에 있던 "앱 기동
시점이 15:35 전이냐 후냐로 갈라 직전 거래일 것을 세팅"이 통째로 필요 없어진다 — 15:35 전이면
캐시가 비어 있으면 그만이고, 그 구간은 어차피 키움 값을 쓴다.

`stock_info`에 종가 컬럼을 더하는 대신 **별도 캐시**로 둔다. `stock_info`는 종목 마스터라 하루에
한 번 바뀌는 성격인데 거기에 매일 바뀌는 가격을 섞으면 무효화 주기가 엉킨다. 위 「제약 — NXT
결과를 스냅샷 테이블에 넣으면 화면이 죽는다」와 같은 이유다.

```
CacheKey.CLOSING_PRICE
값: record ClosingPrices(LocalDate baseDate, Map<String, BigDecimal> priceByStockCode)
적재: sector_price_snapshot에서 snapshot_time이 [15:30, 15:40) 안인 행 중 가장 늦은 시각
```

**`baseDate`를 값에 같이 담는 것이 핵심이다.** 안 그러면 20:00에 적재된 캐시가 다음 날 08:00
수집까지 살아남아 어제 종가로 오늘 등락률을 계산한다. 읽는 쪽이 `baseDate`가 오늘이 아니면
`evict()` 후 다시 적재한다.

적재는 `@Cacheable`에 맡긴다(기존 `StockInfoCacheService`와 같은 모양). 첫 조회 때 DB에서 읽으므로
**기동 훅도 스케줄도 따로 필요 없다.** 아래 「기준가를 15:35로 박지 않는다」대로 15:40 이전에는
캐시를 조회조차 하지 않으므로, 실제 첫 조회는 항상 윈도우가 닫힌 뒤에 일어난다.

`stock_info` 캐시와 **합치지 않는다.** 둘은 바뀌는 시점이 다른데(종목 마스터는 하루 한 번 싱크,
종가는 15:40) 한 덩어리로 묶으면 한쪽이 바뀔 때 다른 쪽까지 버리게 된다. 조회부에서 둘을 같이
읽어 쓰면 된다.

### 기준가를 15:35로 박지 않는다 — 윈도우의 latest를 쓴다

기준가는 "15:35 스냅샷"이 아니라 **`[15:30, 15:40)` 구간에 있는 스냅샷 중 가장 늦은 것**이다.
경계 둘 다 거래소 시간표에서 나온다.

```
15:20  NXT 메인 마감
15:30  KRX 정규장 마감        ← 윈도우 시작
       이 10분은 KRX·NXT 둘 다 닫혀 있어 가격이 변하지 않는다
15:40  NXT 애프터 개장        ← 윈도우 끝, 여기부터 새 기준 적용
```

시각 하나를 상수로 박는 것보다 나은 이유가 셋이다.

1. **수집 주기가 바뀌어도 안 깨진다.** `collect.interval-minutes`를 3분이나 10분으로 바꾸면
   15:35라는 시각 자체가 사라질 수 있다. 윈도우는 주기와 무관하다
2. **8/28처럼 15:35만 없는 날이 분기 없이 풀린다.** 그 윈도우의 latest가 자연스럽게 15:30이
   된다 — "없으면 15:30" 같은 폴백 코드가 따로 필요 없다
3. 그 10분간 가격이 안 변한다는 것이 근거라, 어느 시각이 잡히든 같은 값이다

**아래쪽 경계가 없으면 안 된다.** "15:40 이전의 latest"라고만 하면 8/27처럼 그 구간이 통째로
빈 날에 15:15 같은 **장중 가격**이 잡힌다. 없는 것을 폴백으로 처리할 기회를 잃고 조용히 틀린
기준가를 쓰게 된다.

남는 위험 하나: 주기가 굵어져 윈도우에 15:30만 들어오는 경우다. 15:30은 종가 동시호가 결과가
아직 덜 반영된 값일 수 있다(2026-09-15 지수 15:30 6627.24 대 15:35 6627.26, 종목은 15:30이
98.1~99.7% 일치 대 15:35가 99.7~100%). 감수할 만하고, 어긋나면 눈에 띈다.

경계는 상수로 박지 않는다.

```
market.close-window-start=15:30
market.after-hours-start=15:40
```

### 계산

조회 시점에, 토글이 켜져 있을 때만 돈다.

```
토글 꺼짐               → 키움 flu_rt 그대로            (캐시를 조회하지도 않는다)
15:40 미만              → 토글이 잠겨 있어 이 경우가 없다
15:40 이상 + 기준가 있음 → 등락률 = (현재가 − 기준가) ÷ 기준가 × 100
                          금액   = 현재가 − 기준가
15:40 이상 + 기준가 없음 → 시간외 값 없음 + WARN. 화면은 기본 기준으로 보인다
```

`change_rate`/`change_value`(키움 값)는 **어느 경우에도 건드리지 않는다.** DB에 쓰는 것이 없으므로
건드릴 수가 없다.

기준가가 없는 경우가 실제로 있고, **한 번뿐인 사고가 아니다.** 지수 스냅샷으로 확인한 결손:

```
2026-08-27  15:25 / 15:30 / 15:35 전부 없음  ← 15:20~15:55 수집 구멍
2026-08-28  15:35 없음 (15:30은 있음)
```

두 테이블은 같은 수집 tick(`IndexContributionRankingCollector`)이 쓰므로 종목 쪽도 같이 비어
있다. **8/28은 위 윈도우 규칙이 알아서 15:30을 잡아준다. 8/27은 윈도우가 통째로 비어 기준가가
없다.**

없다고 윈도우를 16:00까지 늘리면 안 된다. 2026-09-14 KRX 애프터마켓 시행 이후 16:00은 이미
시간외 체결가라, 그것을 종가로 쓰면 **기준선이 조용히 틀린 값이 된다.** 윈도우가 빈 날은 그날
시간외 등락률을 포기한다 — 키움 값은 어차피 그 자리에 그대로 있으므로 화면은 기본 기준으로만
보이면 된다.

종목 단위로도 같은 일이 있다 — 15:35에 없다가 15:40에 나타나는 종목(604 대 602). 조용히 0으로
치면 안 된다. 그날 그 종목만 시간외 값이 없는 채로 둔다.

등락률만이 아니라 **금액(현재가 − 기준가)도 같이 계산한다.** 한쪽만 바꾸면 "+500원 (+0.2%)" 같은
앞뒤 안 맞는 표시가 나온다.

경계 시각은 상수로 박지 않는다(`market.close-snapshot-time=15:35`). 15:40으로 옮기고 싶어질 때
숫자 하나만 바꾸면 되는 자리여야 한다.

### 같이 걸리는 것 — 지수 바와 라벨

**1. 마켓 지수 바.** 위 「마켓 지수 바가 같이 걸린다」에 실측과 선택지가 있다. 지수는 15:35에
확정되고 그 뒤 안 움직이므로, 그대로 두면 **지수 바는 전일 대비 값이 고정으로 남고 카테고리 바는
15:35 대비로 움직여 두 막대의 기준이 어긋난다.**

**2. 화면 라벨.** 원래는 "15:40이 되는 순간 모든 숫자가 0 근처로 떨어지는데 무엇 대비인지 안
적으면 장애로 읽힌다"가 걱정이었고, 넣지 않기로 했었다. **결정 3이 이 문제를 없앤다** — 자동으로
갈리는 것이 아니라 사용자가 토글을 직접 누르는 구조라, 무엇을 보고 있는지는 토글 자체가 말해준다.

대신 토글의 **라벨 문구**가 필요해졌다. 「어떻게 부를 것인가」에서 정한 대로 "시간외 등락률" 또는
"장 마감 후 등락률"을 쓴다 — 거래소를 특정하는 표현("NXT 등락률")은 SOR이라 증명할 수 없다.

기준 시각을 응답에 실을지는 그대로 열어둔다. 프론트가 `snapshotTime`으로 직접 추론하게 두면
백엔드가 경계 시각을 바꿀 때 조용히 어긋난다.

### Redis

**지금은 Caffeine 그대로 간다.** `infra/docker-compose.yml`상 백엔드는 단일 컨테이너라 로컬 캐시로
정합성 문제가 없다. 캐시 계약이 이미 `CacheService<T>` + `@Cacheable`로 추상화돼 있어서, 로그인
작업에서 Redis를 도입할 때 `CacheManager` 구현만 갈아끼우면 된다.

다만 그때 이 캐시는 **그대로 옮기면 안 된다.** 지금 형태는 맵 전체를 한 키에 통째로 넣는 구조라
Redis로 가면 매 조회마다 수천 건을 직렬화/역직렬화한다. 종목별 키로 쪼개거나 Caffeine으로 남기는
판단이 그 시점에 필요하다.

## 멀티테넌시 — 카테고리 집계 테이블을 없앤다

회원가입을 도입하면 커스텀 영역(`market_map_category`, `market_map_stock_category`,
`market_value_tier_threshold`)에 `userId`가 붙는다. 그 순간 두 가지가 터진다.

### 터지는 것 1 — 집계 테이블이 사용자 수만큼 곱해진다

`market_map_category_change_rate_snapshot`의 UK는
`(market_type, category_id, market_value_tier_id, snapshot_time)`이다. **`category_id`가 이미
사용자별이 되므로 행이 그대로 사용자 수만큼 늘어난다.**

```
카테고리 × 구간 × 마켓 × 49 tick × 사용자 수
```

행 수보다 나쁜 것은 **쓰기 쪽**이다. 수집 tick마다 `captureCategoryChangeRateSnapshots`가 트리를
빌드하는데, 그걸 사용자 수만큼 반복해야 한다. 5분 격자 안에서 4,300종목 트리를 N번 만든다.
**사용자가 늘수록 수집 시간이 늘고, 어느 지점에서 5분 격자를 깨뜨린다.** 그리고 그중 대부분은
아무도 그 화면을 안 본 사용자 몫이다.

### 터지는 것 2 — 가입할 때 2,700행을 만들어야 한다

`market_map_stock_category`는 지금 **전 종목 미러**다. `MarketMapCategoryService.syncStockCategories`가
`StockInfoSyncedEvent`를 받아 신규 종목마다 행을 만든다. 사용자별이 되면 가입 시점에 2,700행을
한 번에 만들어야 하고, 신규 상장이 있을 때마다 전 사용자에게 뿌려야 한다.

### 결론 — 집계 테이블을 없애고 조회 시점에 계산한다

**근거는 "이미 그러고 있다"는 것이다.** 지도 페이지(`buildCustomMarketMap`)는 그 시각 종목 행을
전부 읽어서(`findPriceByStockCode`, 약 4,300행) 트리를 만든다. 집계 테이블은 "섹터 페이지가
무거워지지 않게" 만든 것인데, **지도 페이지는 그 무거운 경로를 매번 타고 있고 문제가 된 적이 없다.**

그리고 섹터 페이지가 읽는 시각은 **2개(now, before)뿐이다.** 시계열이 아니다
(`findRankingForMarkets`, 엔드포인트는 `/category-change-rates` 하나). 지도가 하는 일을 두 번 하고
그 위에 group-by 한 번이면 같은 값이 나온다.

> **배포 전에 재야 한다.** 위는 코드를 읽고 세운 논증이지 측정이 아니다. 테이블을 지우는 것은
> 되돌리기 어려우므로, `getCustomMarketMap`과 `getCategoryChangeRates`의 실제 응답 시간을 먼저
> 비교한다. 지도 쪽이 이미 느리면 이 논증은 "섹터도 같이 느려진다"가 된다.

### 미리 계산하지 않는 것의 진짜 이득

집계 테이블이 폭발하는 이유는 **사용자 독립적인 측정값**(등락률, 시총)을 **사용자별 매핑**(카테고리)으로
미리 묶어뒀기 때문이다. 둘을 분리하면 사용자별로 저장할 것이 남지 않는다.

| | 성격 | 크기 |
|---|---|---|
| `sector_price_snapshot` | 사용자 독립 | 4,300행 × 49 tick — 지금 그대로 |
| 종목→카테고리 매핑, 구간 경계 | 사용자별 | 수십~수천 행, 거의 안 바뀜 |
| 집계 | 위 둘의 곱 | **저장하지 않는다** |

집계가 필요하면 **(userId, snapshotTime) 키로 메모리 캐시**에 둔다. 그러면 **아무도 안 보는
사용자의 집계는 계산되지 않는다.** 지금 구조는 아무도 안 보는 사용자 몫도 하루 49번 계산해서
저장한다. 사용자 수에 비례하던 비용이 **실제 조회 수**에 비례하게 바뀐다.

텔레그램 발송은 트리 하나(시스템 기본 또는 소유자 것)만 쓰므로 부하가 지금과 같다.

### 가입 비용 — 미러 대신 sparse override

`market_map_stock_category`를 **전 종목 미러가 아니라 override 테이블로** 바꾼다.

```
기본 매핑  = stock_info.categoryName 으로 자동 생성된 카테고리   (지금 getDefaultMarketMap이 쓰는 것)
override = market_map_stock_category 에 행이 있는 종목만
```

신규 가입자는 **0행**으로 시작한다. 옮기거나 별칭을 단 종목만 행이 생긴다. 신규 상장 종목을 전
사용자에게 뿌리는 싱크도 **통째로 사라진다.**

"없으면 이렇게, 있으면 이렇게"가 코드 전체에 번질까 봐 애초에 미러로 출발했는데, **실제로 미러를
전제하는 자리는 한 곳이다.**

```java
// MarketMapQueryService:310 — 없으면 NPE
stockCategoryMap.get(stockInfo.getStockCode()).getCategoryId()
```

이 자리를 resolver 하나로 바꾸면 나머지는 지금 모양 그대로다. 호출부는 여전히 `Map`을 받는다.

```java
/** 한 사용자의 최종 "종목 → 카테고리" 배정. override가 있으면 그것, 없으면 stock_info 업종으로
 * 자동 생성된 카테고리. 호출부는 이 값이 어디서 왔는지 알 필요가 없다. */
Map<String, Long> resolveCategoryByStockCode(Long userId)
```

`toMarketMapItem`의 `resolveAlias`는 **이미 null을 처리한다**(`stockCategory == null || alias == null
|| isBlank`). sparse 전제가 코드에 부분적으로 이미 들어와 있다.

대가: "이 종목이 어느 카테고리인가"를 DB만 보고 알 수 없다. 관리 쿼리가 불편해진다.

### 검토했고 택하지 않은 안

**A. 기본 트리만 집계하고 커스텀한 사용자는 실시간.** 경로가 둘로 갈려 같은 화면이 미묘하게 다른
값을 내는 버그가 생긴다. 지금 「결정 1」에서 피하려는 것과 같은 종류다.

**B. 집계 테이블에 `userId`를 붙이고 감수.** 위 「터지는 것 1」 그대로다. 쓰기 쪽이 사용자 수에
비례해 커지는 구조를 남긴다.

**C. materialized view / 야간 배치 재계산.** 같은 곱셈을 시점만 미룬다. 장중 갱신도 못 한다.

### 텔레그램은 이 범위에 들어오지 않는다

텔레그램 캡션 셋도 전부 이 집계 테이블을 읽는다.

```
섹터 평상시   getTopCategoryRankings             ┐
섹터 08:10    getTopCategoryRankingsByChangeRate ├→ market_map_category_change_rate_snapshot
맵 3건        getMergedTopCategoryRanking        ┘
```

**그런데 전부 간접적으로 읽는다.** 발송기 셋의 의존성에 리포지토리가 하나도 없다.

| | 의존 |
|---|---|
| `SectorTelegramReportSender` | `MarketMapQueryService` + 화면·텔레그램 클라이언트 |
| `MarketMapAlbumReportSender` | 같음 |
| `CategoryRankingTextBuilder` | **없음.** DTO만 받아 문자열로 만든다 |

그래서 바뀌는 것은 **`MarketMapQueryService`의 그 세 메서드 내부**뿐이다. `CategoryRankingSummary`와
`List<TopCategoryItem>`을 돌려주는 계약이 그대로면 **발송기도 텍스트 빌더도 한 줄도 안 바뀐다.**
(PR #109 리뷰에서 "랭킹 확정은 QueryService가 끝내고 빌더는 포맷만"으로 정리해둔 경계가 여기서
값을 한다.)

### 부하는 오히려 준다 — 성격이 바뀔 뿐이다

집계 테이블이 없어지면 **그것을 만드는 일도 같이 없어진다.**

```
지금      수집 tick마다 마켓별 트리 빌드 + 저장 — 하루 145 tick × 2 마켓 ≈ 290회
구획 2    텔레그램 101회 + 실제 화면 조회 수만큼만 계산
```

텔레그램은 tick당 `ALL_STOCK`으로 한 번만 부르고 두 마켓을 함께 받으므로 계산도 한 번이다.

다만 **무거운 계산의 자리가 옮겨간다.** 지금은 수집 tick 안이고, 그 뒤엔 발송·조회 시점이다. 발송은
어차피 수집 직후 같은 호출 안에서 순차 실행되니(`CollectionScheduler`) 같은 자리지만, **화면 조회는
사용자 요청 시간에 직접 얹힌다.** 위 「배포 전에 재야 한다」가 재려는 것이 이것이다.

### 순서 (미확정)

1. 응답 시간 측정 — 지도 페이지 대 섹터 페이지
2. 집계 테이블 제거, 섹터 페이지를 조회 시점 계산으로
3. `market_map_stock_category`를 sparse override로
4. 세 테이블에 `userId` 추가
5. 과거 날짜 조회 — 3·4와 같은 조회 경로를 건드리므로 함께

> 시간외 등락률은 **구획 1에서 수집 시점 계산으로 먼저 나간다.** 한때 "집계를 먼저 없애면 조회 시점
> 계산이 되어 되돌릴 수 있다"는 이유로 순서를 뒤집을지 검토했는데, 정리 배치가 15:40 이후 행을
> 10일 뒤 지우므로 되돌릴 수 없는 범위가 작다고 보고 그대로 두기로 했다. 맨 앞 「구획」을 본다.

## 과거 날짜 조회 (달력)

상단 스냅샷 시각 옆에 달력 아이콘을 이미 붙여뒀다(`MarketMapIcons.CalendarIcon`,
`CategoryChangeRatePage`와 `MarketSummaryPage`). **`cursor-pointer`만 있고 `onClick`이 없는
자리표시자다.** 그걸로 날짜를 골라 과거 마켓맵·섹터를 보게 한다.

### 조회 규칙

정리 배치가 지나간 과거 날짜에는 **종가 스냅샷만 남는다. 마켓별로 하루 한 행씩이다.**
그래서 조회에 고를 것이 없다.

```
그날 그 마켓에 남아 있는 스냅샷 = 종가 스냅샷
없으면 그 날짜는 선택 불가(달력에서 비활성)
```

한때 여기 "15:35 우선, 없으면 15:30"이라는 우선순위를 적어뒀는데, 위 「조치 — 시각을 박지 않고
종가 윈도우의 latest를 남긴다」로 바뀌면서 **하루 한 행만 남아 규칙 자체가 없어졌다.** 어느 시각이
남았는지는 조회하는 쪽이 알 필요가 없다.

단, 정리 배치가 **아직 안 지나간 최근 10일**은 그날의 모든 스냅샷이 남아 있다. 그 구간을 고르면
종가가 아니라 아무 시각이나 잡힐 수 있으므로, 조회 쪽도 같은 윈도우(`[15:30, 15:40)`의 latest)로
골라야 한다. 보존 규칙과 조회 규칙이 같은 식을 쓰게 되는 셈이다.

### 표시 — 사용자에게는 15:30으로 보여준다

**사용자가 정한 방향이다.** 과거 날짜를 보는 사람에게 15:35라는 숫자는 의미가 없고, 15:30이
"장 마감"으로 읽혀서 "이건 그날 종가로 그린 지도구나"가 전달된다는 판단이다. 실제 데이터가
15:35든 15:30이든 화면에는 15:30으로 쓴다.

**다만 미결이다.** 표시 시각과 데이터 시각이 어긋나면, 나중에 "화면은 15:30인데 DB는 15:35"로
디버깅이 꼬인다 — 이번에 보존 시각을 잘못 잡고 있던 것이 정확히 그 종류의 어긋남에서 나왔다.
같은 의도를 시각 대신 **"2026-09-14 종가"**라는 라벨로 전하면 거짓 시각 없이 해결된다.
구현 전에 둘 중 하나로 정한다.

### 백엔드 변경 범위

`GET /api/market-map`이 지금 `market`과 `isCustom`만 받는다. **날짜 파라미터 자체가 없다.**
`MarketMapQueryService.getDefaultMarketMap`/`getCustomMarketMap`도 `findLatestCommonSnapshotTime`으로
"최신"만 집는다. 날짜를 받아 그 날짜의 종가 시각으로 해석하는 경로를 새로 낸다.

`/market-map/category-change-rates`는 이미 시각을 인자로 받으므로(`findRankingForMarkets`) 그쪽은
가볍다.

### 선행 조건

보존 시각이 15:30/15:35 둘로 바뀌고, 실삭제 전환이 끝나야 "과거에는 종가만 남는다"가 실제로
성립한다. 지금은 드라이런이라 과거 날짜에도 5분 간격 스냅샷이 전부 남아 있다.

## 마켓 지수 바의 기준이 카테고리 바와 다르다

섹터 페이지 그래프의 노란 바(마켓 지수)와 회색 바(카테고리)는 **출처가 다른 숫자**다.

| 바 | 출처 | 거래소 |
|---|---|---|
| 회색(카테고리) | 수집한 종목 가격의 시총 가중평균 | SOR (`ka20002`, `stex_tp=3`) |
| 노란(마켓 지수) | 키움 업종현재가가 주는 지수 등락률 | KRX 정규장 (`ka20001`, `stex_tp` 없음) |

**증상 1 — 마감 후 노란 바가 0이다.** 지수는 15:30에 멈추는데 SOR 가격은 20:00까지 움직인다.
"15분 전 대비"라서 딱 0.00%p로 나간다. 하루 49회 발송 중 15:40~20:10 구간이 19회다.

**증상 2 — 장중에도 두 바는 다른 방법으로 계산된 값이다.** KRX 지수는 지수 구성종목·유동주식 기준
산출이고, 회색 바는 우리가 가진 종목 전체의 시총 가중평균이다. 나란히 놓고 "코스피보다 반도체가
앞섰다"고 읽게 되는데 엄밀히는 사과와 오렌지다.

### 선택지

| | 내용 | 상태 |
|---|---|---|
| 1 | 그대로 둔다 | 마감 후 19회는 계속 0 |
| 2 | 0이면 숨긴다 | **접었다.** 장중의 진짜 0과 구분이 안 된다 |
| 3 | 노란 바를 **전체 종목 가중평균**으로 교체 | 회색 바와 방법이 같아져 비교가 성립하고, 시간외에도 움직인다. 대신 "코스피 지수"가 아니게 되므로 라벨을 바꿔야 한다 |
| 4 | "현재"는 지수, "변화율"은 가중평균 | 두 그래프의 기준이 달라져 오히려 헷갈린다 |

**3번이 유력하다.** "지수"라는 이름을 포기하는 대신 두 증상이 한 번에 풀리고, 재료(`ALL_STOCK`
가중평균 경로)가 이미 있다. 위 「시간외 구간 등락률」을 하게 되면 사실상 3번이 전제가 된다.

미결이다. 결정 전이다.

## KRX 프리마켓이 수집 범위 밖이다

2026-09-14부터 KRX에 프리마켓(07:00~07:50)이 생겼다. 그런데 수집 cron이
`0 0/${collect.interval-minutes} ${collect.start-hour}-${collect.end-hour} * * MON-FRI`이고
`collect.start-hour=8`이라 **08:00부터 찍는다.** NXT 프리마켓(08:00~08:50)은 잡히는데 KRX 쪽은
통째로 빠진다.

장 시작 전 움직임을 화면에 보여줄 생각이 있으면 `start-hour`를 7로 내려야 한다. 대가는 이렇다.

- 수집 사이클이 하루 12회 늘어난다(156 → 168). 사이클당 `ka20002` 2회 + `ka20001` 2회
- `sector_price_snapshot`이 하루 5만 행쯤 더 쌓인다(4,303 × 12)
- 텔레그램 발송 기준점(`telegram.send-minute=10`, 기준 시각이 `start-hour:sendMinute`)이 07:10으로
  바뀐다. 발송 격자가 통째로 밀리므로 `send-minute`을 같이 조정해야 한다

**지금 당장 필요하지 않다.** 프리마켓 데이터를 보여줄 화면이 없고, 보여주기로 정하면 그때 바꾼다.
여기 적어두는 이유는 "왜 07시대 데이터가 없나"를 나중에 다시 파지 않기 위해서다.

## 스냅샷의 36%가 화면에 안 쓰인다

`sector_price_snapshot`은 `ka20002` 응답을 **필터 없이 전부** 저장한다. 그런데 화면(마켓맵·섹터)은
`StockInfo.isActiveAndOrdinary()`로 주권만 쓰고, 지수기여도 랭킹도 같은 필터를 쓴다.

2026-09-14 15:30 기준 구성이다.

```
10  코스닥 주권   1,823  ┐
 0  코스피 주권     917  ┘ 2,740   화면이 쓰는 것
 8  ETF          1,168  ┐
60  (미상)         361  │
 6  리츠            23  │ 1,563   저장만 되는 것 (36%)
90  (미상)           8  │
 2  (미상)           2  │
70  (미상)           1  ┘
```

하루 156 사이클 × 1,563 = **약 24만 행**이 매일 쌓인다.

**바로 걷어내지 않는다.** `MarketMapStockCategoryService`(어드민 종목관리)도 이 테이블을 읽고 있어서
거기서 ETF를 쓰는지 확인이 필요하고, 나중에 ETF를 화면에 넣고 싶어질 수도 있다. 보존 기간·보존 시각
얘기와 같이 볼 항목이다.

## `StockMarketCode` enum이 실제와 어긋난다

enum에 **없는** 코드가 실제로 들어오고 있다 — `60`(361건), `90`(8건), `2`(2건), `70`(1건).
`60`은 규모로 보아 ETN으로 보인다. 반대로 enum에 **있는데 한 건도 안 오는** 것도 있다 —
ELW(`3`), 뮤추얼펀드(`4`), 신주인수권(`5`), 하이일드(`9`), K-OTC(`30`), 코넥스(`50`).

**동작은 안전하다.** `isOrdinaryShare`가 코스피(`0`)·코스닥(`10`)만 통과시키는 화이트리스트라
모르는 코드는 자동으로 빠진다. 고칠 것은 enum의 주석이 실제 응답과 다르다는 점뿐이다.

실제로 오는 코드의 정체를 키움 문서에서 확인해 주석을 맞추고, 안 오는 항목은 그렇다고 적어둔다.
