# 가입·로그인 및 사용자별 커스텀 데이터 전환 지시서

작성 기준: 2026-09-25. 구현은 이 문서와 저장소 규칙을 읽은 별도 세션이 진행한다. 이 문서는 구현이 끝나면 삭제하는 작업 지시서다.

## 1. 목표와 확정된 동작

- IP 화이트리스트와 관리자 토큰을 Google 로그인으로 대체한다. Spring Security와 JWT를 사용한다. 계정 역할은 `USER`, `ADMIN`이며, 관리자 화면을 나중에 별도로 만들 수 있도록 역할을 계정에 둔다.
- 비로그인 방문자는 기본 시장 데이터와 요약·지도·섹터 화면을 볼 수 있다. 커스텀 모드는 비활성화한다. 커스텀 페이지를 메뉴에서 누르거나 주소로 직접 열면 로그인 팝업을 보여주고, 성공 후 원래 목적지로 돌아온다.
- 로그인 사용자만 자기 커스텀 모드·커스텀 페이지·설정·스냅샷을 조회·변경한다. URL의 임의 `userId`는 받지 않고 인증 주체에서 사용자 ID를 얻는다. 다른 사용자의 ID가 담긴 요청은 조회와 수정 모두 실패한다.
- 관심종목은 이번 작업에서 사용자별로 바꾸지 않는다. `watch_stock` 테이블과 현재 API는 관리자 전용으로 남긴다. 관심종목 화면·사이드바·메인종목 UI는 관리자에게도 노출하지 않는다. `WatchStockCacheService`의 캐싱은 제거하고, 남는 관리자 API는 직접 조회하게 한다. 비활성 수집기의 캐시 참조는 컴파일되도록 조정하되 수집기 재활성화·관심종목 재설계는 별도 작업이다. 공개 요약 페이지의 `ShortSellingHistorySection`·`ProgramTradingHistorySection`도 `useWatchStocks`를 호출하므로 함께 제거하거나 관심종목 조회 없이 동작하도록 바꾼다. `GET /api/summary`의 대표종목 계산도 전역 관심종목을 읽지 않게 한다.
- 사용자별 커스텀 데이터 개수 상한과 부하·남용 대응(요청 제한, 응답 캐시)은 별도 작업이다. 이번 작업에서 사용자별 신규 캐시를 만들지 않는다. Google OAuth의 `state` 검증과 비밀정보 보호는 인증 기능의 일부로 처리한다.

## 2. 데이터 모델과 이관

### 공통 정보

- `app_user`: 내부 ID, Google 제공자 식별자(`issuer` + `sub`, 유일), 확인된 이메일, `role`, 생성·수정 시각을 둔다. 이메일은 표시용이고 지속적인 계정 키로 쓰지 않는다. 가입은 `USER`만 만들고 관리자 역할 부여는 사용자의 수동 DB 작업으로 남긴다.
- `industry_info(id, name UNIQUE)`: 키움 `ka10099`의 업종명 `upName`을 기준으로 만든 내부 업종 사전이다. `ka10101` 코드를 ID로 쓰지 않는다. 최초 적재와 새 업종 판정은 현재 `StockMarketCode.isOrdinaryShare`와 같은 기준(코스피 `0`, 코스닥 `10`)의 활성 일반주에서 비어 있지 않은 업종명만 사용한다. `stock_info.industry_id`는 이 테이블을 참조한다. 키움 원본에 업종 ID가 없으므로 이름으로 업종을 찾거나 새로 만든다. 빈 업종명은 `industry_id = NULL`로 남기고 수집을 중단하지 않는다.
- 기본 지도는 활성 일반주 `stock_info`와 `industry_info`를 사용한다. 업종명이 빈 종목은 현재 기본 지도와 같이 `미분류` 그룹에 표시한다. 업종명 변경은 해당 종목의 `industry_id`만 새 업종으로 연결하고, 기존 사용자 배정·별칭·섹터 이름을 자동 변경하지 않는다. 롤백 호환 기간에는 `stock_info.industry_name`도 새 코드가 함께 갱신한다.

### 사용자별 정보

- `custom_sector`: `user_id`를 둔다. `industry_id`는 두지 않는다. 이름은 사용자 안에서 유일하다. 부모·스냅샷 참조는 같은 사용자의 행만 가리키도록 복합 FK 또는 동등한 DB 제약을 둔다. 소유자 이관 때 한 트랜잭션에서 참조를 옮길 수 있도록 관련 FK는 지연 검사 가능하게 설계한다. `(user_id, snapshot_id)` 복합 FK의 스냅샷 삭제 동작은 `ON DELETE SET NULL (snapshot_id)`처럼 `user_id`를 유지해야 한다.
- `custom_stock_sector`: `(user_id, stock_code)`가 유일한 명시적 배정이다. `(user_id, sector_id)`가 같은 사용자의 `custom_sector`를 가리키도록 DB에서 보장한다. 행이 없으면 미배정이다. 이 FK도 소유자 이관 트랜잭션에서 지연 검사할 수 있어야 한다.
- `custom_stock_alias`: `(user_id, stock_code)`가 유일한 별도 테이블이다. 배정 없이 별칭만 존재할 수 있다. 기존 `custom_stock_sector.alias` 값은 여기로 이관한다. 구 앱 복귀 가능 기간에는 배정 행이 있는 기존 소유자의 별칭 변경을 구 `alias` 컬럼에도 반영한다. 별칭만 있고 배정이 없는 새 상태는 구 앱에서 표시할 수 없으나 새 테이블 데이터는 보존한다.
- `custom_scale_threshold`, `custom_value_tier_threshold`, `custom_snapshot`에도 `user_id`를 둔다. 기존 전역 유일성 제약은 사용자별 유일성으로 확장한다. V2에서 두 임계값의 **현재 운영값을 한 번** 공통 초기 템플릿으로 복사한다(`default_scale_threshold`, `default_value_tier_threshold` 등). 공개 화면은 이 템플릿을 읽고, 새 계정은 템플릿 행을 자기 `custom_*` 테이블에 복사한다. 이후 소유자의 임계값 변경은 템플릿이나 다른 계정에 전파하지 않는다. 두 임계값은 사용자별 실데이터이고 `user_preference`만 sparse JSON이다.
- `user_preference(user_id PRIMARY KEY, payload JSONB)`는 페이지별 설정의 **사용자 변경분만** 저장하며 가입 시 `{}`를 만든다. 서버가 기본값의 유일한 출처다. 저장은 payload 전체 교체와 500ms 디바운스를 사용하고 페이지별 값은 독립이다(`docs/backlog.md`의 결정).
- 별칭, 배정, 섹터, 임계값, 선호 설정과 스냅샷은 모든 조회·변경·캐시에서 사용자 범위를 적용한다. 섹터 ID·스냅샷 ID를 넘겨받는 API는 반드시 소유자를 확인한다. 섹터의 부모 변경도 서로 다른 사용자를 연결하지 못하게 한다.

### 기존 데이터의 소유자

- V2에서 `app_user.id = 999999`인 이관 전용 행을 명시적으로 만들고 기존 `custom_*` 행을 그 ID에 연결한다. PostgreSQL identity 컬럼에 지정 ID를 넣을 때는 `OVERRIDING SYSTEM VALUE` 등 명시 삽입 문법을 사용하고, 해당 ID가 이미 없는지 먼저 검증한다. 종목 배정은 자동 생성된 행까지 **전부 보존**한다. 별칭은 별도 테이블로 복사한다.
- 구 서버가 V2 적용 후에도 쓸 수 있도록 새 사용자 컬럼의 임시 기본값은 `999999`로 둔다. 임시 계정은 Google `issuer`/`sub`가 없어 로그인할 수 없다.
- 사용자가 Google로 정상 가입하면 별개의 실제 계정 ID가 생기고 업종 섹터 등 기본 행이 생성된다. **앱이 기존 데이터를 자동으로 주장하거나 ADMIN 역할을 자동으로 주지 않는다.** 공개 전 임시 가입 게이트는 배포 환경변수의 소유자 이메일 한 개와 Google의 `email_verified=true`를 검사한다. 이 이메일은 게이트에만 쓰고 영구 계정 키로 쓰지 않는다. 사용자는 가입 계정의 ID·Google 제공자 식별자, 다른 가입자 0명 여부, 양쪽 데이터 행 수를 읽기 전용 쿼리로 확인한 다음 검증된 일회성 이관 SQL을 수동 실행한다. 게이트는 이관·ADMIN 확인 뒤 공개 전환 직전에 해제한다.
- 그 SQL은 한 트랜잭션에서 실제 계정의 가입 초기 행을 확인·정리하고, 중복 이름·임계값 키 충돌이 없음을 확인한 뒤, 기존 소유자 `999999`의 섹터·배정·별칭·임계값·스냅샷·선호 설정의 `user_id`를 실제 계정 ID로 옮긴다. 관련 복합 FK는 `SET CONSTRAINTS ... DEFERRED`로 트랜잭션 끝에 검사한다. 이어 실제 계정의 `role`을 `ADMIN`으로 바꾸고, 구 앱 롤백 시 쓰기가 실패하지 않도록 임시 컬럼 기본값도 실제 ID로 바꾼다. 검증 실패 시 전체 롤백한다. `999999` 행 삭제는 기본값 교체와 FK 확인 이후에만 한다.
- 소유자 이관이 끝나기 전에는 임시 가입 게이트를 유지하고 공개 nginx 전환을 하지 않는다. 이관 전 기존 데이터는 다른 사용자에게 보이지 않아야 한다. 사용자 수동 DB 작업은 **읽기 전용 확인 쿼리 → 결과 판정 → 정확한 이관 SQL → 사후 확인 쿼리** 순서로 안내한다.

## 3. 초기화·수집·편집의 동작

### 가입

1. Google 인증 결과의 `issuer`/`sub`로 기존 계정을 찾고 없으면 `USER`로 만든다. 같은 콜백 재시도는 계정·초기 데이터를 중복 생성하지 않는다.
2. `industry_info`의 이름을 새 사용자의 루트 `custom_sector`로 일괄 `INSERT … SELECT … ON CONFLICT (user_id, name) DO NOTHING` 한다. 종목 수천 건의 `custom_stock_sector`는 만들지 않는다.
3. `user_preference` 빈 행과 공통 템플릿에서 복사한 사용자별 임계값 행을 준비한다. 화면 설정의 기본값은 서버 코드에 두고 사용자가 바꾼 값만 JSON에 저장한다. 가입 초기 적재와 새 업종 전파는 같은 DB 잠금/직렬화 경계를 사용해 동시 실행 시 누락이 없게 한다. 모든 기존 업종을 전체 사용자에게 주기적으로 다시 채우는 조정 작업은 금지한다. 사용자가 의도적으로 삭제한 섹터를 되살리기 때문이다.

### 07시 `stock_info` 수집

- 활성 일반주에서 새 업종명이 관찰될 때 `industry_info`에 유일 키로 삽입하고 해당 종목의 `industry_id`를 설정한다. **새 업종 행이 실제로 생긴 경우에만** 업종 생성 이벤트를 낸다. 지도 대상이 아닌 종목이 같은 이름을 먼저 갖고 있더라도 업종 생성 이벤트를 선점하지 않게 한다.
- 이벤트 처리에서는 전체 사용자에게 같은 이름의 루트 `custom_sector`를 일괄 `INSERT … SELECT … ON CONFLICT DO NOTHING` 한다. 중복은 정상 스킵이므로 오류·경고 로그를 만들지 않는다. 업종 삽입과 전파를 같은 트랜잭션에서 완료하거나 실패 시 함께 롤백한다. 가입 초기 적재와 동일한 DB 잠금/직렬화 경계를 사용한다. 전파 성공 후 삭제된 섹터를 이벤트 재시도로 되살리지 않는다.
- 새 종목이 기존 업종에 들어오면 사용자의 배정 행은 만들지 않는다. 과거에 해당 이름의 커스텀 섹터를 사용자가 지웠더라도 새 종목 때문에 재생성하지 않는다. 기존의 종목별 자동 동기화 이벤트는 제거한다.
- 종목이 비활성화되면 사용자 배정·별칭을 즉시 일괄 삭제하지 않는다. 활성 화면에서 제외한다.

### 조회·저장·삭제

- 종목 관리 목록은 활성 일반주 `stock_info`를 기준으로 업종명을 표시한다. 해당 사용자의 배정·별칭이 있으면 붙이고 없으면 빈 값 또는 `-`로 표시한다. 커스텀 지도·섹터 집계에는 명시적으로 배정된 활성 종목만 넣는다. 기본 지도는 업종 기준으로 집계한다.
- 단건·일괄 배정은 없는 `(user_id, stock_code)` 행도 만들 수 있는 upsert다. 배정 해제는 해당 행을 삭제한다. 별칭 저장은 별도 테이블의 upsert이고, 별칭 제거는 별칭 행만 삭제한다. 배정 해제는 별칭을 지우지 않는다.
- 섹터 삭제는 **그 사용자**의 삭제 대상 하위 트리에 연결된 `custom_stock_sector`만 검사한다. 활성 종목의 배정이 있으면 삭제를 막는다. 비활성 종목의 배정은 같은 트랜잭션에서 정리한 뒤 삭제한다. 별칭은 유지한다. 기본 업종이나 다른 사용자의 배정은 삭제 검사의 대상이 아니다.
- 스냅샷은 `custom_sector`, `custom_stock_sector`, `custom_stock_alias`, 임계값과 `user_preference`를 **전체 저장·전체 복원**한다. 부분 저장·부분 복원 UI/API는 만들지 않는다. 복원은 한 트랜잭션에서 현재 사용자의 커스텀 데이터만 교체하며, 종목 코드는 `stock_info`의 현행 행과 검증한다. `industry_info`와 `stock_info`는 복원하지 않는다. 이전 형식의 스냅샷은 DB에 그대로 두되 새 목록에서 숨기고, 직접 복원 요청은 명확한 오류로 거절한다. 새 형식에는 버전 필드를 둔다.

## 4. 인증과 공개 경계

- Google OAuth/OIDC에서 `state`와 Google 토큰 검증을 사용한다. API 액세스 JWT는 15분, 회전형 리프레시 토큰은 14일로 하고 리프레시 토큰은 해시·만료·폐기 시각을 DB에 저장한다. 브라우저 JS가 읽지 못하는 `HttpOnly`, `Secure`, `SameSite=Lax` 쿠키로 전달하며 로그아웃 시 리프레시 토큰을 폐기한다. 변경 요청은 CSRF/Origin 검사를 적용한다. OAuth 콜백과 토큰 재발급은 명시적으로 허용하고 나머지 쓰기 요청은 인증한다. 로그와 URL에 사용자 토큰·Google 자격증명을 남기지 않는다.
- 공개: 정적 SPA, OAuth 시작·콜백, 로그인 상태 확인, 기본 시장 조회. `/api/map?isCustom=false`는 공개한다. `isCustom=true`는 인증된 사용자만 허용한다. `/api/map` 하위의 제외·리셋 변경과 사용자별 임계값·설정 조회는 경로가 `custom`이 아니어도 사용자 범위를 적용한다. 비로그인 화면에 필요한 기본값은 공통 기본값으로 내려준다.
- 인증 필요: `/api/custom/**`, 사용자 선호 설정, 커스텀 모드의 모든 API. 관리자 필요: `/api/watch-stocks/**`와 이후 추가할 실제 관리자 API. `GET /api/summary` 등 공개 API가 관리자 관심종목이나 사용자 커스텀 값을 노출하지 않는지 확인한다. 관심종목 UI는 역할과 관계없이 제거하고, 비로그인 요약 페이지에서 `/api/watch-stocks` 요청 자체가 발생하지 않아야 한다.
- `domain/access`의 IP·관리자 토큰 API와 nginx `auth_request`는 최종 전환에서 제거한다. 사용자 개인화 API의 이름은 `/api/admin/market-map/*`에서 `/api/custom/*`로 바꾸고 DTO의 `category* → sector*`, `version* → snapshot*`도 `docs/backlog.md`의 목록대로 바꾼다. 지도 응답의 `categoryId`는 그대로 둔다.
- 프론트는 `useIsAdmin` 기반 커스텀 메뉴를 로그인 사용자 메뉴로 전환한다. 메뉴는 비로그인에게도 보이되 클릭하면 로그인 팝업을 연다. 직접 URL·새로고침에도 같은 보호를 적용한다. 로그아웃·계정 전환 때 React Query의 사용자별 데이터와 저장된 커스텀 모드 상태를 비워 다른 계정 화면이 잠시 보이지 않게 한다. 비로그인에는 저장된 `marketMap.isCustom=true`가 있어도 유효 모드를 `false`로 강제한다. 로그인 직후에는 서버의 `user_preference`를 먼저 불러오고 초기 로드가 끝나기 전 디바운스 저장을 막는다. 기존 `sessionStorage` 값은 계정 간 섞일 수 있으므로 자동 업로드하지 않는다. 기존 소유자의 브라우저 전용 화면 설정은 서버 기본값에서 다시 선택한다.
- 텔레그램 렌더러는 소유자 계정의 설정으로 캡처한다(`docs/backlog.md`의 기존 결정). 백엔드는 짧은 수명의 읽기 전용 캡처 토큰을 `/capture` 요청 본문으로 렌더러에 보내고, 렌더러는 캡처 탭에 API 경로 전용 쿠키 또는 동등한 헤더를 설정한다. 토큰을 URL의 `path` 쿼리에 넣지 않는다. 현재 `renderer/server.js`가 오류 때 `path`를 로그에 남기기 때문이다. 탭마다 인증 상태를 격리하고 캡처 완료 시 폐기한다. 공개 기본 화면 캡처와 소유자 커스텀 캡처를 구분한다.

## 5. 구현·배포 순서

1. **V2 스키마 전용 PR:** `src/main/resources/flyway/V2__*.sql`부터 시작한다. V1은 수정하지 않는다. `app_user`, `industry_info`, 별칭·선호·리프레시 토큰 저장 테이블 및 사용자 컬럼·인덱스·FK를 추가하고 기존 데이터를 이관한다. 현재 운영 임계값이 실제로 존재하는지 읽기 전용 쿼리로 선확인한 뒤 그 값을 공통 초기 템플릿으로 고정한다. 값이 비어 있으면 임의 기본값을 만들지 말고 V2 적용을 중단해 사용자에게 결과를 전달한다. 구 앱이 계속 읽고 쓰는 컬럼은 유지한다. 전역 유일성 제약을 사용자별 제약으로 넓히는 경우에도 구 앱의 단일 소유자 쓰기가 계속 성공하는지 검증한다. 먼저 main 병합·배포하고 Flyway 성공을 확인한다.
2. **백엔드 기능 PR:** 인증, 산업 정보 수집, 사용자 범위, 스냅샷, 공개/관리자 API를 구현한다. V2와 배포 간격에 들어온 업종·별칭은 새 코드가 사용하기 전에 멱등 보정한다. 롤백 호환 기간에는 `stock_info.industry_name`과 기존 배정 행의 `alias`를 함께 갱신한다. 기존 프론트가 남아 있는 동안 `/api/admin/market-map/*`는 소유자 전용 임시 호환 경로로 유지한다. 구 IP 게이트와 임시 소유자 가입 게이트도 공개 전환 전까지 유지한다.
3. **렌더러·프론트 기능 PR:** 렌더러 `/capture`에 선택적 캡처 토큰을 받는 호환 기능을 먼저 배포한다(`target=renderer` 별도 실행). 구 백엔드의 토큰 없는 요청도 이 단계에서는 계속 처리한다. 소유자 데이터 이관 전에는 새 계정의 빈 커스텀 데이터를 텔레그램 캡처에 사용하지 않는다. 프론트는 로그인 팝업·세션 상태·공개 기본 화면·커스텀 보호를 구현한다. `marketMapAdmin.ts`, `useMarketMapAdmin.ts` 등의 이름을 custom으로 바꾸고 IP 관리 `AdminPage`, 옛 `/admin/market-map` 페이지를 제거한다. 백엔드·렌더러·프론트 계약을 통합 검증한다.
4. **소유자 수동 이관과 공개 전환:** 실제 계정 가입 후 사용자가 확인 쿼리의 결과를 공유하면 이관 SQL을 확정한다. 사용자가 수동 실행한 뒤 역할·행 수·화면을 확인한다. **그 후** 백엔드의 소유자 캡처 토큰 발급·전달을 활성화하고 `target=renderer`의 실제 지도·섹터 캡처를 확인한다. 그다음 임시 가입 게이트를 해제하고 nginx의 정적/API IP `auth_request`를 제거한다. nginx 일반·guest 설정의 공개 경계를 일치시킨다. 인증·커스텀 API는 Spring Security가 지킨다. 이후 별도 정리 PR로 임시 구 API·`domain/access`·구 컬럼·임시 기본값을 제거한다. 이 정리에서 필요한 Flyway도 스키마 전용 PR을 먼저 병합·배포한다.

**롤백 순서:** 공개 nginx로 전환한 뒤에는 구 백엔드 이미지만 먼저 되돌리면 예전 관리자 API가 외부에 노출될 수 있다. 먼저 nginx의 IP 게이트를 복구·확인한다. 소유자 이관만 끝나고 다른 사용자 데이터가 없는 동안에는 구 앱 복귀를 별도로 검증할 수 있다. 다른 사용자의 동일 이름 섹터가 생긴 뒤에는 구 앱이 사용자별 데이터를 구분하지 못하므로 구 백엔드로 단순 롤백하지 않는다. 이때는 새 인증 백엔드를 유지하고 프론트/nginx만 되돌리거나, 접근을 막은 상태에서 수정 후 재배포한다. DB 데이터 이관을 역방향으로 자동 롤백하지 않는다.

## 6. 검증과 완료 기준

- V2 적용 전후 기존 앱의 기동, 기존 커스텀 읽기·쓰기, Flyway history를 확인한다. 사용자별 FK와 유일성 제약은 DB 통합 테스트로 검증한다. `999999`의 섹터·배정·별칭·임계값·스냅샷 행 수를 가입 전후와 수동 이관 전후에 비교한다. 가입 초기 행과 이름이 충돌해도 이관 전체가 원자적으로 성공하거나 롤백되는지 검증한다.
- 비로그인 기본 요약·지도·섹터는 정상 응답하고, 커스텀 API와 `isCustom=true`는 거부된다. 비로그인 요약 화면은 관심종목 API를 호출하지 않는다. 일반 사용자는 관리자 관심종목 API를 읽거나 바꿀 수 없다. 사용자 A의 섹터·종목·별칭·스냅샷 ID로 사용자 B가 접근하는 테스트를 넣는다. 스냅샷 삭제가 `user_id`를 NULL로 바꾸지 않는지도 DB 테스트로 확인한다.
- 가입은 업종 수만큼 섹터만 만들고 배정은 0건이다. 같은 Google 콜백·업종 생성 이벤트를 재시도해도 중복이 없다. 가입과 업종 생성의 동시 실행에서도 누락이 없다. 새 종목은 배정 0건, 새 업종은 모든 계정에 섹터 1개씩 생긴다. 삭제한 기존 업종의 섹터는 새 종목·스냅샷 복원 뒤의 전역 재조정 때문에 다시 생기지 않는다.
- 소유자의 현재 커스텀 지도가 이관 전후 동일하다. 별칭만 있는 종목, 없는 배정을 upsert하는 단건·일괄 저장, 비활성 배정이 있는 섹터 삭제, 전체 스냅샷 복원과 타 사용자 불변을 확인한다.
- 로그아웃·다른 계정 로그인·직접 URL·새로고침에서 이전 계정의 화면·React Query 캐시가 보이지 않는다. 렌더러의 지도와 섹터 이미지가 소유자 설정으로 생성되고 토큰이 로그에 남지 않는다.
- 구현 세션은 `docs/rules/process.md`, `style.md`, `testing.md`, `operations.md`를 따른다. 컴파일·테스트·포맷·프론트 빌드와 수동 확인 결과를 각 PR에 남긴다. 사용자에게 DB 확인이 필요하면 **읽기 전용 쿼리 → 결과 판정 → 필요한 수동 조치** 순서로 진행한다. 코드 구현과 PR 병합·배포는 별도 담당이다.
