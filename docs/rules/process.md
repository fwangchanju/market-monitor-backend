# 작업 진행 프로세스

## 이 문서의 전제

**사용자는 코드를 직접 읽지 않는다.**

예전에는 사용자가 한 줄씩 확인하면서 진행했고, 그래서 "세부 작업마다 멈춰서 확인받는다", "빌드·테스트
실행은 기본 동작이 아니다" 같은 규칙이 있었다. 지금은 그 전제가 사라졌다.

그래서 이 문서의 모든 규칙은 하나의 원칙에서 나온다.

> **사람이 리뷰를 안 하면, 그 자리를 자동 검증이 메워야 한다.**

코드 수정 후 컴파일·테스트·포맷 검사를 돌리는 것은 **선택이 아니라 기본 동작**이다. 그것이 유일한
검증 수단이기 때문이다.

---

## 역할

| 역할 | 현재 담당 | 하는 일 |
|---|---|---|
| **설계·문서·리뷰** | Opus | 대화 정리, 범위·완료 기준 정의, 문서 작성, PR 리뷰 |
| **구현** | Sonnet | 문서와 지시서를 읽고 코드 작성, 리뷰 반영 |
| **결정** | 사용자 | PR 병합, 배포 시점 |

모델이 바뀌면 **이 표의 "현재 담당" 칸만** 고친다. 다른 문서에는 모델명을 적지 않는다.

문서(`docs/**`, `CLAUDE.md`)는 **설계·문서 역할이 쓴다.** 구현 역할은 문서를 읽기만 하고,
작업 중 알게 된 것은 **PR 설명에** 남긴다.

이 분리에는 이유가 있다. 작업 중인 쪽은 자기가 방금 한 일이 다 중요해 보여서, 문서에 구현 세부사항을
계속 쌓는다. 실제로 이전 `docs/history.md`가 그렇게 오염됐다. 기록 여부를 판단하는 주체를 작업자와
분리해야 문서가 깨끗하게 유지된다.

---

## 작업 단위

- **기능 하나 = 브랜치 하나 = PR 하나**
- 기준은 "오늘 한 일 전부"가 아니라 **"되돌릴 단위"**다. 세 가지를 했으면 세 PR이고, 그중 하나만
  문제면 그것만 병합하지 않으면 된다
- 성격이 다른 작업(기능 추가 / 버그 수정 / 정리)을 한 PR에 섞지 않는다. 섞으면 정리하다 뭔가 깨졌을 때
  기능 추가까지 같이 되돌아간다

---

## 작업 플로우

```
1. 대화 정리        착수 전, 그때까지 나온 의도·제약·접은 선택지를 정리한다
2. 범위 확정        할 것 + "안 할 것"
3. 완료·검증 정의   무엇이 되면 끝인가, 어떻게 확인하는가
4. 지시서 작성      1~3을 파일로 남긴다
5. 코드 작성
6. 리뷰 ↔ 반영      왕복 상한 1회
7. 병합             사용자가 한다
8. 회수             "다음에 또 설명해야 할 것"만 골라 문서에 반영한다
```

### 1. 대화 정리

작업 착수 전에, 그때까지 대화에서 나온 **의도·제약·선호**를 정리한다.

**결론뿐 아니라 검토했다가 접은 선택지와 그 이유도 함께 남긴다.** 결론만 적으면 나중에 "왜 이렇게
했지?" 하면서 되돌리게 되고, 같은 논의를 처음부터 반복하게 된다.

### 2. 범위 확정

할 것과 **안 할 것**을 모두 적는다. **금지 목록이 허용 목록보다 중요하다.**

의도적으로 남겨둔 코드(미사용이지만 나중에 쓸 것), 곧 갈아엎을 예정이라 지금 손대면 낭비인 영역 등이
여기 해당한다. 이게 안 적혀 있으면 구현하는 쪽은 당연히 "정리 대상"으로 판단하고 지운다.

### 3. 완료·검증 정의

**코드를 짜기 전에** 정한다. 뒤에 정하면 이미 짠 코드에 맞춰 검증을 꿰맞추게 된다.

- 무엇이 되면 끝인가
- 어떻게 확인하는가 — **테스트로 확인할 것**과 **배포 후 수동 확인이 필요한 것**을 나눈다

### 4. 지시서 작성

1~3을 **파일로** 남긴다. 대화에만 있으면 컨텍스트가 압축될 때 사라지고, 그 뒤부터는 기억나는 대로
즉흥 진행하게 된다.

지시서는 **휘발성 문서**다. 작업이 끝나면 삭제한다. 영속 문서(`docs/rules/*`, `decisions.md`,
`architecture.md`, `operations.md`)와 섞지 않는다.

### 5. 코드 작성

- 지시서와 `docs/architecture.md`를 따른다
- 판단이 갈리는 지점이 나오면 멈춰서 묻지 말고 **합리적인 쪽을 선택해 진행하고, 그 선택과 이유를 PR
  설명에 남긴다.** 되돌리는 건 사용자가 PR을 보고 결정한다
- 다음 두 경우에만 멈추고 확인한다
  - 지시서와 실제 코드가 명백히 모순돼서 진행이 불가능할 때
  - 되돌리기 어려운 작업(데이터 삭제, 마이그레이션)의 범위가 지시서에 적힌 것보다 커질 때

### 6. 리뷰 ↔ 반영

리뷰는 PR에 코멘트로 단다. 지적은 두 종류로 구분한다.

| 구분 | 대상 | 처리 |
|---|---|---|
| **차단(Blocking)** | 동작이 틀렸다 / 지시서와 다르게 구현했다 / 테스트가 없다 | 반드시 수정 |
| **제안(Non-blocking)** | 네이밍·구조 취향 | 코멘트만 남기고 **그대로 병합**. 나중에 정리 |

**왕복은 PR당 최대 1회.** 2회차에도 안 맞으면 리뷰어가 직접 고치고 그 사실을 PR에 남긴다.
상한이 없으면 리뷰가 라인바이라인으로 회귀한다.

### 7. 병합

**사용자만 한다.** 어떤 경우에도 직접 병합하지 않는다.

### 8. 회수

작업 중 나온 것 중 **"다음에 또 설명해야 할 것"만** 골라 문서에 반영한다.

| 성격 | 어디에 |
|---|---|
| 이번에 내린 결정과 그 이유, 접은 선택지 | `docs/decisions.md` |
| 이번에 안 하기로 하고 미룬 일 (배경·구상·선행 조건 포함) | `docs/backlog.md` |
| 앞으로 지켜야 할 규칙이 된 것 | `docs/rules/*` |

전부 기록하지 않는다. "중요한 건 다 적어라"로 기준을 잡으면 구현 세부사항이 계속 쌓여서 문서가
쓸모없어진다.

**미룬 일은 목록만 적지 않는다.** 나중에 그 일을 시작할 때 "어떻게 하려고 했더라"를 다시 떠올리며
설명하지 않아도 되게, 배경과 구상까지 함께 남긴다.

## 단계 건너뛰기 방지

사용자가 급하거나 귀찮을 때 4~5단계로 바로 점프하는 일이 생긴다. 그대로 따라가면 범위도 완료 기준도
없이 코드가 나오고, 결국 나중에 더 큰 비용으로 돌아온다.

**그래서 이건 지시받는 쪽이 막아준다.**

### 언제 발동하나

코드 변경 요청을 받았는데, 그 작업에 대해 다음이 정해지지 않았을 때.

- 범위(할 것 / 안 할 것)
- 완료·검증 기준

### 예외 — 그냥 진행한다

- 파일 2개 이하, 수십 줄 이내의 국소 수정
- 오타·로그·주석 수정
- 이미 합의된 작업의 후속 수정(리뷰 반영 등)

반대로 아래는 크기와 무관하게 **반드시** 1~3단계를 거친다.

- 새 파일·새 패키지가 생기는 작업
- DB 스키마 변경
- 외부 연동 추가
- 배포·인프라 설정 변경

### 발동 시 행동

1. **요청을 거절하지 않는다.** "이것부터 정하고 가는 게 어떻겠냐"고 제안한다
2. 무엇이 빠졌는지 구체적으로 말한다 (범위인지, 완료 기준인지, 둘 다인지)
3. 사용자가 그대로 진행하라고 하면 **진행한다.** 대신 PR 설명에 **"범위/완료 기준 정의를 생략하고
   진행함"**을 남긴다

3번이 중요하다. 강제하면 규칙 자체가 지워지고, 기록이 없으면 나중에 문제가 생겼을 때 원인을 추적할 수
없다.

## 완료 기준 (Definition of Done)

PR을 올리기 전에 아래를 전부 만족해야 한다.

1. `./gradlew compileJava compileTestJava` 통과
2. `./gradlew test` 통과 (매뉴얼 테스트 제외)
3. `./gradlew spotlessApply` 실행 후 `spotlessCheck` 통과
4. 컴파일 경고가 작업 전보다 **늘지 않았을 것**
5. PR 설명에 변경 내용·이유·검증 방법이 적혀 있을 것

---

## PR 설명 형식

사용자는 코드를 보지 않는다. **PR 설명이 유일한 판단 근거다.**

- **무엇을 바꿨는가** — 파일 단위가 아니라 동작 단위로
- **왜 바꿨는가**
- **어떻게 검증했는가** — 실행한 명령, 추가한 테스트, 배포 후 확인이 필요한 항목
- **판단이 갈렸던 지점과 선택한 이유** (있는 경우)
- **절차를 생략했다면 그 사실** (있는 경우)

---

## 커밋

- 커밋 메시지 형식은 `docs/rules/commit.md`를 따른다
- **PR을 올리기 전에 브랜치 안에서 커밋을 의미 단위 1~3개로 정리한다.** 작업 중 나온 "수정",
  "오타" 같은 커밋은 남기지 않는다
- 이 레포는 **squash merge를 쓸 수 없다.** `release.yml`의 `promote-main` job이 머지 커밋의
  `HEAD^2`로 원본 브랜치 tip을 찾아 이미지를 승격시키기 때문이다. 그래서 커밋 정리는 병합 시점이
  아니라 **PR을 올리기 전 브랜치 안에서** 해야 한다
- **포맷 변경은 별도 커밋으로 분리한다.** `spotlessApply`가 수십 개 파일을 건드리면 실제 작업 diff가
  묻힌다

---

## 커밋/푸시 전 확인

- 현재 브랜치에 열려 있는 PR이 있으면 그 사실을 알리고, 기존 PR에 이어붙일지 확인한다
- 열린 PR이 없으면, 새 브랜치를 만들기 전에 현재 브랜치가 이미 main에 병합됐는지 확인한다
  (`git merge-base --is-ancestor <현재 브랜치 HEAD> origin/main`). 병합된 브랜치는 낡은 것이므로
  main 기준으로 새로 만들면 된다
- 병합 이력도 없고 열린 PR도 없다면(커밋만 push되고 PR이 없는 상태), 그 커밋들이 어디에도 안 걸린 채
  남을 수 있으니 어떻게 처리할지 확인한다

---

## 배포는 병합과 분리되어 있다

**main에 병합해도 자동으로 배포되지 않는다.** 병합 시점에는 이미지 태그 승격만 일어나고, 실제 배포는
사용자가 원하는 시점에 수동으로 실행한다.

이유: 배포하면 서버가 잠시 내려가는데, 사용자가 웹을 실제로 쓰고 있다. 배포를 병합에 묶어두면
"PR을 잘게 나눈다 = 다운타임이 늘어난다"가 되어서, 코드 관리 방식이 배포 사정에 끌려다니게 된다.

자세한 절차는 `docs/operations.md`.

## DB 마이그레이션 규칙 (예외 없음)

이 작업 플로우에서 가장 위험한 지점이다.

Flyway는 기본 설정상, DB의 `flyway_schema_history`에 "적용됨"으로 기록된 마이그레이션 파일이 지금 앱의
classpath에 없으면 **시작 자체를 거부한다.** 그래서 브랜치에서 새 마이그레이션까지 같이 시험 배포했다가
문제를 발견해 main으로 롤백하면, main의 jar엔 그 파일이 없으니 **앱이 아예 못 뜬다.** "롤백하려다 전체
장애"가 되는 최악의 시나리오다.

1. **마이그레이션이 포함된 작업은 항상 2단계로 나눈다.**
   ① 마이그레이션 스크립트만 먼저 main에 병합하고 실제로 배포해서 DB에 적용해둔다.
   ② 그 스키마를 사용하는 기능 코드는 그 다음에 별도 브랜치에서 개발·시험배포한다.
   이러면 브랜치를 아무리 굴리다 main으로 롤백해도 main은 항상 그 마이그레이션을 알고 있는 상태다.

2. **마이그레이션은 항상 하위호환(추가만) 되게 작성한다.**
   - 안전: nullable 컬럼 추가, 새 테이블 추가
   - 금지: 기존 컬럼 삭제, 타입 변경, 기본값 없이 NOT NULL 강제
   - 근거: JPA는 엔티티가 매핑한 컬럼만 명시적으로 SELECT하므로(`SELECT *`를 쓰지 않음) DB에 모르는
     컬럼이 더 있어도 조회는 무해하다. `ddl-auto=validate`도 "엔티티가 필요로 하는 컬럼이 DB에 있는지"만
     검사한다. 깨지는 유일한 지점은 INSERT인데, 새 컬럼이 NOT NULL이면서 기본값이 없을 때만 예전 코드의
     INSERT가 제약 위반으로 실패한다

이 두 규칙은 배포·롤백 플로우가 성립하기 위한 전제 조건이라 예외를 두지 않는다.

`V1__create_schema.sql`을 계속 고쳐쓰는 현재 방침과 그 리스크는 `docs/decisions.md`와
`docs/operations.md`를 참고한다.
